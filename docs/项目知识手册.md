# 项目知识手册

> 目标：不是让你背代码，而是能从需求、架构、环境、编码、测试、排障到面试复述完整理解项目。  
> 当前边界：基础设施、Web/API骨架、MediaMTX基础链路和YOLO CPU工程基准已实现；独立视频源、Worker、Tracker、Redis Streams、VLM、RAG、音频和告警闭环仍待开发。

## 1. 先建立完整心智模型

### 1.1 一次告警未来如何产生

1. 摄像头把视频发布到 MediaMTX。
2. Capture Worker拉流、解码、抽帧并维护环形缓冲。
3. 集中的Inference Worker加载YOLO，Tracker维持目标身份。
4. Event Producer根据轨迹变化、ROI和时间间隔筛选候选事件。
5. 候选JSON写入Redis Stream，VLM Consumer通过Consumer Group异步处理。
6. VLM结合Chroma检索到的规则返回结构化结论。
7. Saver把截图/录像放MinIO，把事件、告警和审计记录写MySQL。
8. Redis Pub/Sub把新告警通知给SSE页面。
9. Prometheus记录耗时、积压和资源，结构化日志用trace_id串联全过程。

当前完成的是地基、媒体基础验证和离线YOLO性能基准，不是持续运行的第1～7步完整AI业务。

### 1.2 每个组件只做一类事

| 组件 | 存什么/做什么 | 不应该做什么 |
|---|---|---|
| MySQL | 任务、告警、规则等结构化数据 | 存大段视频二进制 |
| Redis | 短期消息、缓存、实时通知 | 作为唯一永久业务记录 |
| MinIO | 图片、视频、音频、PDF 对象 | 复杂关系查询 |
| MediaMTX | 媒体协议接入和分发 | 执行 YOLO/VLM |
| Flask | API、页面和管理控制 | 在请求线程里长期跑视频循环 |
| YOLO | 快速定位目标 | 可靠理解复杂行为语义 |
| VLM | 理解场景、行为和规则 | 高频处理每一帧 |

## 2. 必备网络知识

### 2.1 IP、端口与 localhost

IP 标识一台网络主机，端口标识主机上的具体服务。`127.0.0.1`/`localhost` 只表示“当前网络命名空间自己”。

- 宿主机 Python 访问 Docker Redis：`127.0.0.1:6379`。
- Compose 中另一个容器访问 Redis：`redis:6379`，不能写 `127.0.0.1`，因为那会指向调用方容器自己。
- MySQL 的 `3307:3306` 表示宿主机访问 3307，容器内仍监听 3306。

### 2.2 TCP、UDP、HTTP

TCP 可靠、有连接，HTTP、MySQL、Redis、RTSP 控制通常基于 TCP。UDP 不保证到达，但延迟低，WebRTC 媒体常用 UDP。HTTP 是请求—响应协议；SSE 是保持 HTTP 连接让服务器持续单向推消息。

### 2.3 RTSP、HLS、WebRTC、MJPEG

| 协议 | 特点 | 适用 |
|---|---|---|
| RTSP | 摄像头常见，低延迟，浏览器不原生支持 | 摄像头接入、分析进程拉流 |
| HLS | HTTP 分片，兼容和稳定性好，通常延迟秒级 | 回放、兼容预览 |
| WebRTC | 浏览器原生、低延迟，网络穿透配置更复杂 | 实时监控预览 |
| MJPEG | 连续 JPEG，简单但带宽高、无音频、扩展性弱 | 调试或极简预览 |

企业产品不一定只选一个：常见做法是 RTSP 接入，WebRTC 低延迟预览，HLS 兼容/回放。MediaMTX 的价值是统一接入和多协议输出。

## 3. Docker 从零入门

### 3.1 四个概念

- **Image 镜像**：只读模板，例如 `redis:7-alpine`。
- **Container 容器**：镜像运行出来的进程实例。
- **Volume 数据卷**：独立于容器生命周期的持久化数据。
- **Network 网络**：Compose 自动建立内部网络，服务可用服务名互访。

### 3.2 为什么使用 Compose

单个 `docker run` 参数很多，容易忘。Compose 把镜像、端口、卷、环境变量和启动命令写进 `docker-compose.yml`，可版本化并一键重建环境。

### 3.3 本项目启动与检查

在项目根目录执行：

```powershell
docker compose pull
docker compose up -d
docker compose ps
```

查看日志：

```powershell
docker compose logs --tail 100 redis
docker compose logs --tail 100 mysql
docker compose logs --tail 100 minio
docker compose logs --tail 100 mediamtx
```

停止但保留数据：

```powershell
docker compose stop
```

停止并删除容器/网络，但保留 named volume：

```powershell
docker compose down
```

`docker compose down -v` 会删除数据卷，意味着数据库和对象数据丢失，不要在有价值数据时执行。

### 3.4 四个服务是怎样创建的

#### Redis

```yaml
redis:
  image: redis:7-alpine
  ports: ["6379:6379"]
  volumes: ["redis_data:/data"]
  command: redis-server --appendonly yes
```

Alpine 镜像小；AOF 把写命令追加到磁盘，提高重启恢复能力。检查：

```powershell
docker exec vlm-redis redis-cli ping
```

#### MySQL

```yaml
mysql:
  image: mysql:8.4
  ports: ["3307:3306"]
  environment:
    MYSQL_ROOT_PASSWORD: ${MYSQL_ROOT_PASSWORD}
    MYSQL_DATABASE: video_analyzer
  volumes: ["mysql_data:/var/lib/mysql"]
```

`${...}` 表示从环境读取。当前仓库 Compose 仍是开发硬编码值，建议按此方式整改。检查时让客户端交互输入密码，避免口令进入 shell history。

#### MinIO

MinIO API 用 9000，管理控制台用 9001，数据放 `/data`。`server /data --console-address ":9001"` 同时启动对象 API 和控制台。

#### MediaMTX

映射 RTSP 8554、HLS 8888、WebRTC 8889 和 ICE UDP 8189，并把宿主机 `mediamtx.yml` 挂载进容器。当前显式开放 `pedestrian` 发布路径；已验证本地 RTSP 发布/拉流、OpenCV 取帧和 HLS 解码，WebRTC 只验证页面入口。

首次发布曾返回 400。服务端日志提示 `path 'pedestrian' is not configured`，因此修复方式是在 `mediamtx.yml` 中声明路径，而不是更换 FFmpeg 编码参数：

```yaml
paths:
  pedestrian:
    source: publisher
```

直接 `-c copy` 发布原视频时，客户端可能从 GOP 中间加入，出现参考帧告警。生产演示建议 25 FPS 下设置 `-g 50 -keyint_min 50 -sc_threshold 0`，每 2 秒生成关键帧，改善首帧、HLS 切片和中途加入稳定性。

Docker 场景还要注意 RTSP 的“控制连接”和“媒体数据”不一定走同一连接。当前 Compose 只映射 `8554/tcp`，因此客户端应显式指定 RTSP over TCP；若客户端默认选择 UDP，就可能因为动态 RTP/RTCP UDP 端口没有映射而超时。服务端日志中的 `with TCP` 或 `with UDP` 是定位这类问题的直接证据。

### 3.5 Compose 中的密码如何管理

不要把真实密码提交到 Git。开发环境可在根目录 `.env` 保存 Compose 变量，并把 `.env` 加入 `.gitignore`；提交 `.env.example` 只放占位符：

```dotenv
MYSQL_ROOT_PASSWORD=replace_with_local_password
MINIO_ROOT_USER=replace_with_local_user
MINIO_ROOT_PASSWORD=replace_with_local_password
```

生产环境使用 Docker Secret、云 secret manager 或部署平台加密变量，遵循最小权限；应用不要长期使用 MySQL root。

## 4. Python 项目基础

### 4.1 包、模块、导入

`.py` 文件是模块，带 `__init__.py` 的目录是包。`from core.db import db` 会加载模块并取得全局 SQLAlchemy 对象。导入代码会执行模块顶层语句，所以顶层不应做昂贵或不可控操作。

### 4.2 虚拟环境和依赖

虚拟环境隔离项目包：

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
```

`requirements.txt` 固定版本便于复现，但其中 AI 包较重。阶段一只运行基础模块时仍可能安装全部依赖；后续可拆 `requirements-base.txt`、`requirements-ai.txt`、`requirements-dev.txt`。

### 4.3 函数、类、类型提示

`def get_result(key: str) -> Optional[Any]` 表示参数预计是字符串，返回任意值或 `None`。类型提示帮助 IDE 和读者，不会自动阻止错误类型；Pydantic 才会在运行时解析/验证数据。

### 4.4 异常处理

`try/except` 应在能决定如何恢复的边界使用。只捕获 `Exception` 并返回 `None` 很方便，但可能掩盖故障。更好的做法是定义 `InfrastructureError`，让 API/Worker 决定重试、降级或失败。

## 5. YAML、环境变量与配置优先级

YAML 适合层级配置，缩进表示归属，不能随意混 Tab。环境变量是进程外的字符串，适合端口、地址和 secret。

本项目流程：`.env` → 进程环境；`default.yaml` → 默认业务参数；`get_settings()` 用环境变量覆盖关键值；Pydantic 转为 `int/bool/float` 等类型。

示例：

```powershell
$env:MYSQL_PORT='3307'
$env:YOLO_DEVICE='cuda'
python app.py
```

PowerShell 变量只对当前进程及其子进程有效。修改后若 settings 已缓存，需要重启程序。

## 6. HTTP、REST 与 JSON

### 6.1 请求组成

HTTP 请求包括方法、URL、headers 和可选 body。JSON 请求要带 `Content-Type: application/json`。REST 常用：GET 查询、POST 创建/动作、DELETE 删除。

### 6.2 常见状态码

- `200 OK`：成功查询或动作。
- `201 Created`：创建成功。
- `400 Bad Request`：格式或参数错误。
- `401 Unauthorized`：未登录；`403 Forbidden`：已识别但无权限。
- `404 Not Found`：资源不存在。
- `409 Conflict`：重复或状态冲突。
- `422 Unprocessable Entity`：JSON 合法但字段不符合业务模型。
- `500`：服务端未处理异常。

### 6.3 API 为什么要做入口校验

数据库字段长度不是友好的 API 规则。入口应明确校验必填、类型、长度、枚举、URL、数组大小和坐标范围，并返回稳定错误码。不要用“截断一切”掩盖客户端错误。

## 7. Flask 知识与调用链

### 7.1 Flask app、Blueprint、route

Flask app 是应用对象；Blueprint 是一组可复用路由。`api_bp` 注册到 `/api` 后，声明的 `/tasks` 实际路径是 `/api/tasks`。装饰器 `@api_bp.route(...)` 把 URL 和 Python 函数绑定。

### 7.2 request 与 response

`request.get_json(silent=True)` 尝试解析 JSON，失败返回 `None`。`jsonify()` 生成 JSON Response 并设置正确 MIME。返回 `(response, 201)` 指定状态码。

### 7.3 Application Context

Flask-SQLAlchemy 需要知道当前 app 配置，因此测试里使用 `with app.app_context():`。离开上下文后再访问懒加载 ORM 属性可能报错。

### 7.4 应用启动调用链

```text
导入 app.py
 → setup_logging()
 → get_settings()
 → create_app()
 → init_db(app)
 → db.create_all()
 → 注册 metrics/Blueprint/routes
 → WSGI server 接收请求
```

`db.create_all()` 适合初期建空表，不是迁移工具；字段改动后必须使用 Alembic。

## 8. 数据库核心知识

### 8.1 表、行、列和主键

表定义一类实体；行是一条记录；列是字段；主键唯一标识记录。自增整数主键简单高效，对外分布式接口未来可加 UUID。

### 8.2 外键和关系

`alarm_records.task_id` 指向 `analysis_tasks.id`，保证告警属于存在的任务。ORM relationship 让代码可写 `task.alarms` 和 `alarm.task`。

### 8.3 事务

事务保证一组数据库操作要么全部成功，要么全部回滚。流程是修改 session → `commit()`；异常时必须 `rollback()`。MySQL 事务不能自动回滚已经上传到 MinIO 的文件或已经发布到 Redis 的消息，这就是分布式一致性问题。

### 8.4 索引和分页

索引像书的目录，能加快查询但增加写入和磁盘成本。`task_id`、`status`、`created_at` 已有部分索引。Offset 分页越到后面越慢；大数据使用游标分页。

### 8.5 ORM 与 SQL 注入

ORM 通常把值作为参数而不是拼进 SQL，因此任务名中的 SQL 字符串不会作为命令执行。但动态表名、排序字段、原生 SQL 仍可能注入，必须白名单或参数化。

## 9. Redis 核心知识

### 9.1 List 队列与生产者消费者

生产者生成任务，消费者异步处理。队列削峰：视频瞬间产生很多候选时，Web/Producer 不必等待 VLM 全部完成。

`RPUSH + BLPOP` 保持 FIFO；`BLPOP timeout` 可以阻塞等待，减少空转 CPU。

### 9.2 TTL 缓存

TTL 是键的生存时间。VLM 相似结果缓存可以降低成本，但必须考虑数据陈旧、Prompt 版本和规则变化。缓存键应包含输入摘要和版本。

### 9.3 Pub/Sub

发布者不关心有几个订阅者，在线订阅者收到消息。它不保存消息，离线订阅者收不到，所以不能替代可靠队列。

### 9.4 可靠消息问题

- **消息丢失**：消费者弹出后崩溃。
- **重复消费**：重试时同一任务执行多次。
- **积压**：生产速度大于消费速度。
- **毒消息**：固定输入每次都失败。

解决思路：ACK、visibility timeout、重试上限、死信队列、幂等键、队列深度告警和背压。Redis Streams 更适合展示这些机制。

## 10. MinIO/S3 核心知识

Bucket 类似顶层容器，object key 类似对象名称，但不是传统磁盘目录。`alarms/1/a.jpg` 的斜杠只是 key 的一部分，控制台把它展示成目录。

`Content-Type` 告诉浏览器对象是 JPEG、MP4 还是 PDF。Presigned URL 在有限时间内携带签名，允许用户不持有 MinIO 密钥也能下载私有对象。

一致性流程应记录 object key 和上传状态；定期扫描“数据库无记录的孤儿对象”和“数据库指向但对象不存在”的断链。

### 10.1 普通上传、Multipart与断点续传

- `put_object()`可上传字节流；`fput_object()`从本地文件流式上传。
- MinIO Python SDK会根据对象大小自动选择Multipart，减少内存占用并满足S3大对象上传要求。
- SDK自动Multipart只解决“这一次服务端上传怎么传”，不自动解决“用户断网、浏览器刷新、服务重启后如何续传”。
- 业务级断点续传必须持久化`upload_id`、每个`part_number`和MinIO返回的`ETag`，完成时提交完整分片清单。
- 浏览器应通过Presigned PUT URL直传MinIO，Flask只负责权限、签名和状态；否则大视频会占满Web Worker、内存和网络带宽。

### 10.2 删除与生命周期

单对象删除用于明确资源回收；批量删除要逐项记录成功和失败。删除接口应幂等：重复删除一个不存在的对象，不应制造新的业务错误。

生命周期规则适合按前缀和天数自动过期，例如测试文件、临时上传和过期告警证据；但生命周期不能代替业务删除，因为系统仍需同步MySQL状态、保留审计并处理法律留存期。

MySQL和MinIO之间没有分布式事务。实际工程常用软删除、异步Cleaner、重试/死信、幂等键与定期对账实现最终一致性。

### 10.3 MinIO加密的三层含义

1. **传输加密**：HTTPS/TLS，防止文件与凭据在网络中明文传输，生产环境必须启用。
2. **服务端加密**：SSE-S3由存储服务管理密钥；SSE-KMS通过KES/Vault等外部密钥系统管理；SSE-C由客户端每次请求提供密钥，管理难度更高。
3. **客户端加密**：应用使用AES-GCM先加密再上传，MinIO只看到密文；安全边界最强，但预览、转码、YOLO/VLM分析前都要解密。

本项目首版优先TLS、私有Bucket、最小权限Access Key、短期Presigned URL和Secret管理；SSE-S3/SSE-KMS作为生产增强，客户端加密不进入首版，避免为了“技术多”破坏可用性。

### 10.4 对象存储测试清单

- 正常：上传、下载签名、元数据、单删、批量删除、Multipart完成。
- 异常：MinIO不可用、超时、权限不足、磁盘满、哈希不一致、数据库事务回滚。
- 边界：空文件、最大文件、最后一个小分片、重复删除、对象不存在、同key并发上传。
- 安全：越权签名、伪造MIME/扩展名、恶意文件头、超大分片、伪造ETag、过期upload_id、日志泄露签名URL。
- 并发：同一上传会话并发完成、批量删除部分失败、Cleaner重复消费和Presigned URL高并发签发。

## 11. 日志与可观测性

可观测性三支柱通常是 metrics、logs、traces：

- Metrics 告诉你“系统整体是否异常”。
- Logs 告诉你“具体发生了什么”。
- Traces 告诉你“一个请求/任务跨组件经过了哪里”。

Prometheus 拉取 `/metrics`。Counter 算速率，Gauge 看当前状态，Histogram 看延迟分布。P95 表示 95% 请求不超过该时延，不是平均值。

建议告警：队列持续增长、VLM 错误率、端到端 P95、断流次数、GPU 温度/显存、数据库连接池等待、MinIO 上传失败。

## 12. 并发基础：进程、线程、协程

### 12.1 区别

- **进程**：独立内存，隔离强，通信成本高；适合视频循环和独立 Worker。
- **线程**：共享进程内存，I/O 并发方便；Python CPU 密集代码受 GIL 影响，但 PyTorch/OpenCV 的底层计算常释放 GIL。
- **协程**：单线程事件循环协作切换，适合大量网络 I/O；阻塞库会卡住整个事件循环。

### 12.2 本项目怎么选

Flask/Waitress 用线程处理 HTTP；AI Worker 用独立进程隔离长任务；Redis 传递消息；VLM 网络调用可在线程池或 async 客户端中限并发。GPU 不适合每个进程各加载一份模型，否则显存迅速耗尽，通常一个 GPU 推理进程集中批处理。

### 12.3 竞态、锁与幂等

两个执行单元同时修改共享状态可能产生竞态。数据库用事务/唯一索引，Redis 用原子命令，Python 共享内存才考虑 Lock。业务幂等表示同一消息执行两次，最终只产生一份告警；可用唯一 `event_id` + 数据库唯一约束实现。

### 12.4 背压

系统最慢环节决定吞吐。若 VLM 每秒处理 1 条，Producer 每秒产生 10 条，队列必然增长。背压可以降低抽帧率、合并同目标事件、丢弃过期低优先级任务或扩容消费者。

## 13. AI 模型知识

### 13.1 YOLO

YOLO 输出目标类别、置信度和 bounding box。`confidence` 控制候选阈值，NMS/IoU 去掉重叠框。阈值高会减少误报但增加漏报，必须在业务数据集上调优。

评估指标：Precision、Recall、mAP；系统指标：预处理/推理/后处理耗时、FPS、显存、P95。安全场景通常更关注 Recall，但误报过多会造成告警疲劳。

### 13.2 跟踪

检测回答“这一帧有什么”，跟踪回答“不同帧中的框是不是同一个目标”。ByteTrack 用检测框和运动关联 track id，可做持续时间规则、去重和轨迹判断。

### 13.3 VLM

VLM 同时理解图像和文本。Prompt 应包含任务、场景、规则、输出 schema 和“不确定时怎么做”。不要只问“图中发生了什么”，否则输出难稳定。

单帧适合静态状态，多帧适合动作。局部裁剪看细节，全景看上下文。结构化 JSON 仍需运行时校验，因为模型可能输出多余文字、缺字段或错误类型。

### 13.4 推理加速

- FP32：精度高、显存和计算开销大。
- FP16：RTX GPU 常用，显存约减半并加速；需验证精度。
- ONNX Runtime：跨框架推理和图优化。
- TensorRT：NVIDIA GPU 深度优化，速度高但构建和兼容成本更高。
- Batch：提高吞吐但增加等待和显存；实时系统常用动态小 batch。

正确比较方式：相同模型、输入、预热次数、硬件和数据，分别记录 P50/P95、FPS、显存与精度变化。

### 13.5 RTX 4050 笔记本注意事项

显存有限且可能受功耗/温度影响。优先小型 YOLO、FP16、单 GPU Worker；VLM 可优先 API 或小型量化模型。启动时预热，监控温度和显存，OOM 时降分辨率/模型/batch，而不是让进程直接崩溃。

## 14. 音频分析知识

FFmpeg 从视频抽取音轨；统一转换 16 kHz、mono、PCM 便于模型处理。VAD 判断是否有人声，ASR 把语音变文字，声学事件分类识别玻璃破碎、警报等非语音声音。

音频切块要保留开始/结束时间戳，并与视频时间轴对齐。边界重叠可避免事件正好被切断。两级检测比所有音频都交给大模型更省资源。

## 15. RAG 与向量数据库

Embedding 把文本映射为向量，语义相近的文本距离较近。RAG 先检索规则，再把相关规则交给 VLM，降低凭空回答。

- FAISS：本地向量索引库，性能好但元数据/服务需自己管理。
- Chroma：开箱即用、持久化和元数据方便，适合单机作品集。
- Milvus：分布式、高并发和运维能力强，本项目当前过重。

切块太大导致检索不准，太小丢上下文。规则文档要保存来源页码/条款，VLM 告警才能给出可核验证据。

## 16. 安全知识与当前漏洞

### 16.1 XSS

攻击者让浏览器执行恶意脚本。当前页面把 API 数据拼进 `innerHTML`，存在存储型 XSS 风险。修复不是在数据库删除 `<script>`，而是在输出上下文安全编码，优先 `textContent`，加 CSP 和浏览器测试。

### 16.2 SQL 注入

攻击输入改变 SQL 结构。ORM 参数化通常安全，但原生 SQL、动态排序字段仍需白名单。最小权限数据库账号可降低成功注入后的损失。

### 16.3 SSRF 与路径遍历

SSRF 是让服务器请求攻击者指定地址，可能访问云元数据或内网。路径遍历用 `../` 越过允许目录。媒体源读取前应规范化路径、限定根目录、限制协议/IP、解析 DNS 后再次检查、限制重定向和响应大小。

### 16.4 CSRF、CORS、鉴权和授权

CSRF 利用已登录浏览器发起非本人意愿操作；CORS 规定哪些网页来源能读取响应，不是身份认证。鉴权确认“你是谁”，授权确认“你能做什么”。项目生产化应加入登录、RBAC、SameSite/CSRF Token、来源白名单和操作审计。

### 16.5 上传安全

不能只看 `.pdf` 扩展名；检查文件头、MIME、大小、页数，随机化 object key，禁止可执行文件，必要时杀毒/沙箱解析。解析器应限时限内存，防止恶意 PDF。

## 17. pytest 测试知识

### 17.1 fixture

fixture 准备共享环境。`yield client` 前是 setup，后是 teardown。清理必须只删除本测试拥有的数据，不能清空开发库。

### 17.2 断言与隔离

断言应验证外部行为，而不是实现细节。XSS 用例最初按同名数量断言，受历史数据污染；改为使用创建返回 ID，这是更稳定的测试标识。

### 17.3 测试金字塔

- 单元测试：快、隔离，测试纯函数。
- 集成测试：连接 MySQL/Redis/MinIO，验证组件协作。
- 端到端：浏览器、媒体流和 AI 全链路，慢但贴近用户。

当前以集成测试为主。后续应增加纯函数单测和少量高价值 E2E。

### 17.4 并发和性能指标

Concurrency 是同时在途的工作量；Throughput 是单位时间完成数；Latency 是单次耗时。平均值会掩盖长尾，因此看 P50/P95/P99。压测要报告机器、数据、预热、持续时间、错误率和请求模型。

## 20. 排障方法

### 20.1 固定顺序

1. 明确现象、期望和最近改动。
2. 判断故障层：浏览器、Flask、Redis/MySQL/MinIO、媒体、模型。
3. 看日志和状态码，不先猜。
4. 用最小命令验证下层依赖。
5. 构造最小复现并记录输入。
6. 修根因，补回归测试。
7. 再跑相关测试和全量测试。

### 20.2 常见问题

| 现象 | 检查 | 常见原因 |
|---|---|---|
| MySQL 连接拒绝 | `docker compose ps`、3307 端口 | 配置仍写 3306、容器未 ready |
| Redis 超时 | `redis-cli ping`、host | 容器内错误使用 localhost |
| MinIO 403 | endpoint/access key/系统时间 | 凭证错、签名过期、时钟偏差 |
| Flask 启动时报指标重复 | 是否多次 `create_app` | 全局 Prometheus Registry 重复注册 |

| 页面弹出异常脚本 | 检查 `innerHTML` | 存储型 XSS |
| 队列越来越长 | 生产/消费速率、错误率 | VLM 慢、消费者挂、无背压 |
| GPU OOM | 显存、模型、分辨率、batch | 多进程重复加载、batch 过大 |
| WebRTC 播不了 | UDP 8189、ICE 地址、防火墙 | NAT/候选地址配置错误 |

## 21. 测试发现漏洞的思考过程

阶段一不是跑一次 pytest 就结束，而是从失败反推系统边界：

1. 多次建 app 出现 Prometheus 重复注册，说明第三方全局资源与应用工厂生命周期不一致。
2. 空 JSON/非法状态暴露入口校验缺失，于是补 400 和白名单。
3. TTL 测试要求真正过期，促使缓存写入使用原子 `SET EX`。
4. XSS 用例偶发失败，定位为共享数据库历史污染，改用返回 ID 精确断言。
5. XSS 字符串在 JSON 中安全并不等于浏览器安全；继续检查模板发现 `innerHTML` 风险。
6. 路径遍历字符串只是被保存，因为尚未读媒体，所以该测试不能证明 SSRF/路径防护完成。

面试中讲这个过程，比只说“52 个测试全过”更能体现工程判断。

## 22. 面试高频问题与回答框架

### 为什么 YOLO 后还要 VLM？

YOLO 适合高频目标定位，但对复杂行为和规则语义能力有限；VLM 理解强但慢且贵。两级架构用 YOLO 缩小候选，VLM 只处理关键片段，在效果、成本和延迟间平衡。

### 为什么 Redis，不直接函数调用？

视频生产速度和 VLM 消费速度不同。队列解耦、削峰并允许独立扩缩容。当前 List 适合原型，但生产可靠性要升级 ACK、重试、死信与幂等。

### 为什么 MySQL + MinIO？

MySQL 管结构化关系和事务，MinIO 管大对象。数据库保存 object key，实现查询能力和存储成本的平衡。

### 为什么 MediaMTX？

摄像头常用 RTSP，浏览器需要 WebRTC/HLS。MediaMTX 以较低维护成本统一协议和分发，避免自己实现媒体服务器。

### 如何解决并发？

先按瓶颈拆进程；Redis 做边界；GPU 单 Worker/小 batch 避免重复加载；VLM 限并发；数据库连接池有上限；队列积压触发背压。并发正确性依靠原子命令、事务、唯一约束和幂等，不只靠加线程。

### 当前最大风险是什么？

当前无鉴权且页面有动态 `innerHTML`，媒体源未来还有 SSRF/路径风险，Redis List 无 ACK，MySQL/Redis 双写不可靠。因此当前只适合本机开发，生产前优先解决安全和可靠性，而不是先换更大模型。

### 如何证明优化有效？

建立固定视频输入和基线，在相同硬件下比较FPS、各阶段耗时、P95、显存、端到端延迟、积压和VLM成本。若没有人工标注真值，不宣称YOLO Precision、Recall、漏检率或误检率，只做抽样定性检查；以后有标注集再补模型质量对比。

## 24. Redis Streams可靠消费知识

Redis List的`BLPOP`会在取出时删除消息；消费者取出后崩溃，消息可能永久丢失。Streams的Consumer Group把“已投递未确认”记录在Pending Entries List中：

1. Producer用`XADD ai:candidate:v1 * ...`写事件。
2. Consumer用`XREADGROUP GROUP vlm-consumers worker-1 ...`读取。
3. 成功写出结果后才`XACK`。
4. Worker崩溃后，其他消费者用`XAUTOCLAIM`接管超时Pending消息。
5. 超过最大重试次数写入`ai:dead_letter:v1`，保留失败原因和原消息ID。

ACK只能减少丢失，不能保证“恰好一次”。消费者可能处理成功但在ACK前崩溃，所以消息会再次投递。真正的幂等依靠稳定`event_id`、数据库唯一约束和“已处理则返回已有结果”。

## 25. 状态机、快照与版本治理知识

状态机的价值是限制不合法变化，例如`stopped`不能直接变`running`，必须先`starting`。转换应集中在服务层，而不是每个路由随意赋值。

配置快照解决“历史漂移”：任务今天使用YOLOv8n和Prompt v1，明天改成v8s和Prompt v2，昨天的告警仍应能说明实际使用了什么。TaskRun保存启动时配置，AIEvent和Alert再保存实际模型、Prompt和RAG版本。

版本表中的历史记录只禁用，不物理删除。否则告警外键失效，面试时也无法解释模型结果如何复现。

## 26. MySQL与MinIO最终一致性

MySQL事务不能自动包含MinIO对象操作。若“先删数据库再删对象”，对象删除失败会产生孤儿；若“先删对象再删数据库”，数据库提交失败会留下指向不存在对象的记录。

本项目采用可补偿状态：

```text
active -> delete_pending -> deleting -> deleted
                           \-> delete_failed -> 重试
```

Cleaner周期扫描`delete_pending/delete_failed`并重试MinIO删除；孤儿扫描比较Bucket对象和数据库Key；所有操作按对象ID幂等。这里追求的是最终一致，而不是引入重型分布式事务。

## 28. Capture Worker、线程与实时背压知识

### 28.1 Producer/Consumer 是什么

Capture Worker 是 Producer（生产者），负责产生帧；下一阶段 Inference Worker 是 Consumer（消费者），负责取帧运行 YOLO。中间缓冲可以隔离摄像头抖动和推理耗时。

没有缓冲时，Capture 必须等待 YOLO，推理变慢会阻塞读流并可能导致 RTSP 堆积或断流。无限队列在消费者长期慢于生产者时又会耗尽内存。因此实时视频通常使用有界队列并明确“满时丢旧帧”或“满时阻塞”。本项目选择丢旧帧，因为在线告警更关注低延迟；逐帧完整处理属于另一种离线任务语义。

### 28.2 Python 线程、锁和 Event

- `Thread`：让 Capture 循环在后台运行，Flask 请求无需一直等待。
- `Lock`：保护状态字段、会话字典和 `deque`，防止并发读写不一致。
- `Event`：线程安全的停止信号。调用 `set()` 后循环在安全点退出，比强行杀线程更容易释放资源。

线程设置 `daemon=True` 只用于避免开发进程被永久阻塞，不等于可以忽略资源释放。正常关闭仍要 `stop()`、`join()` 和 `release()`。

Python 有 GIL 也不代表组合操作自动安全。“判断长度、删除旧项、追加新项”包含多个步骤，必须在同一把锁中完成。耗时的 `VideoCapture.read()`、JPEG 编码和 YOLO 推理不能长期持有状态锁，否则状态 API 也会被阻塞。

### 28.3 `VideoCapture` 和 FFmpeg 各做什么

`cv2.VideoCapture` 是 OpenCV 的统一视频读取接口。传文件路径时读取 MP4 容器，传 `rtsp://...` 时接收网络流，大致完成：

```text
打开文件/网络 → 解析容器或协议 → 读取压缩包 → 解码 → 输出 BGR NumPy 图像
```

FFmpeg 和 OpenCV 不是互相替代。FFmpeg 是完整媒体工具和库生态，本项目用命令行 FFmpeg 裁剪、探测和发布视频；OpenCV 内部可借助 FFmpeg 后端解码，并把图像直接交给 Python/YOLO。

常用操作：

- `isOpened()`：检查是否打开成功。
- `read()`：返回成功标志和一帧 BGR 图像。
- `CAP_PROP_POS_FRAMES`：本地视频帧位置。
- `CAP_PROP_POS_MSEC`：源时间轴毫秒位置。
- `CAP_PROP_FPS`：源帧率，用于文件节流。
- `release()`：释放文件、Socket 和解码器资源。

### 28.4 RTSP 推流和拉流链路

RTSP 是实时流控制协议，常见地址为 `rtsp://localhost:8554/demo`。测试链路是：

```text
test.mp4
  → FFmpeg 读取并按实时速度编码/封装
  → 推送到 MediaMTX 的 RTSP 地址
  → MediaMTX 接收、协议转换和分发
  → OpenCV Capture Worker 拉流并解码
```

MediaMTX 不负责把实时视频永久存入 MinIO。它是媒体服务器；MinIO 是对象存储，用于告警截图、证据片段和离线上传文件。实时主链路经过 MediaMTX 进入 AI，只有有价值的证据才异步保存到 MinIO。

### 28.5 FPS 节流、EOF 和重连

本地文件没有天然实时速度限制。25 FPS 的帧间隔约为：

```text
1 / 25 秒 = 0.04 秒 = 40 ms
```

每帧等待约 40 ms，页面才像实时视频。这里使用 `Event.wait(timeout)`，停止信号到来时可提前返回；单纯 `sleep()` 必须等满时间。

EOF 表示文件读到结尾。演示任务可以回到开头循环，离线批处理则应结束。RTSP 通常没有正常 EOF，失败多半来自网络抖动、发布端停止或解码异常，需要重新打开连接。重连必须有次数、间隔和最终错误状态，不能无限高频重试。

### 28.6 有界缓冲和内存估算

1080p 未压缩 BGR 单帧内存约为：

```text
1920 × 1080 × 3 bytes = 6,220,800 bytes ≈ 5.9 MiB
```

容量 4 仅像素数据就约 23.7 MiB；若 20 路视频各保留 30 帧，内存会迅速达到数 GiB。因此容量必须小且固定，停止时要 `clear()` 解除 NumPy 数组引用。

`deque` 适合两端快速插入和删除。本项目在一把锁内完成容量判断、`popleft()` 和 `append()`，保证 Producer 与预览/推理 Consumer 并发时结构一致。

### 28.7 MJPEG multipart 协议

MJPEG 是连续发送独立 JPEG 图片，响应类型为：

```http
Content-Type: multipart/x-mixed-replace; boundary=frame
```

响应体反复出现：

```http
--frame
Content-Type: image/jpeg

<JPEG bytes>
```

浏览器收到下一张图后替换上一张，所以普通 `<img>` 就能播放。它简单直观，但带宽高、缺少音视频同步和成熟弱网能力，不作为正式大规模播放方案。

### 28.8 两类状态为什么暂时不同

- `TaskRun.status`：MySQL 中的持久控制面状态，用于审计和历史记录。
- Runtime 状态：Worker 内存中的即时执行状态，用于判断线程是否真的连接和读帧。

API 接受启动请求只说明指令已受理，不能证明视频已打开，所以数据库先进入 `starting`。只有 Worker 成功连接并发送心跳后，持久状态才应转成 `running`。该同步将在独立 Worker 和 Redis 心跳阶段实现。

### 28.10 常见面试追问

**为什么帧不放 Redis？** 1080p 未压缩帧很大，Base64 还会额外膨胀约三分之一，浪费 Redis 内存、网络和序列化 CPU。帧在处理进程内用有界缓冲传递；跨进程只传事件元数据和对象 Key。

**为什么不用无限队列保证不漏帧？** 在线告警重视时效。输入快于推理时，无限队列必然让内存和延迟增长，最后输出过期告警。需要逐帧处理的离线任务应使用可回放、可持久化的批处理链路。

**为什么当前用线程？** OpenCV 读流属于 I/O 和底层库工作，线程实现简单，适合单机原型。生产时按故障隔离和扩缩容拆为独立进程/容器，但不改变 `FramePacket`、背压和状态机设计。

**42 个丢帧是不是性能问题？** 当前没有 Consumer，容量 4 的缓冲收到 46 帧后只保留最新 4 帧，所以 42 是符合预期的背压结果。接入 YOLO 后才结合输入 FPS、推理 FPS、丢帧率和 P95 判断瓶颈。

## 29. 集中式推理、性能指标与检测预览知识

### 29.1 模型实例、权重和显存

加载 YOLO 不只是把 `.pt` 文件读入内存，还会构造网络层、参数张量、设备上下文和推理中间结果。若每个视频任务各创建一个模型，相同权重会重复占用 RAM/显存。集中式 Worker 将“视频任务数量”和“模型实例数量”解耦：多路输入可以共享一个模型，扩容时按设备能力增加 Worker 实例。

CPU 联调固定使用 `model_weights/yolov8n.pt`、`device=cpu`、`half=False`。FP16 是 16 位浮点，常用于 GPU 降低显存和提升吞吐；CPU 并不一定受益，且不同算子支持程度不同。显卡恢复后应分别测试 CUDA FP32 与 FP16，不应只因设备可见就自动切换。

### 29.2 Round Robin 与任务公平性

Round Robin（轮询）按循环顺序给任务处理机会，复杂度低且行为可解释。`deque.popleft()` 取队首，再 `append()` 放队尾，就形成环形调度。空任务可以跳过，有帧任务每轮最多处理一帧，避免单路高 FPS 输入饿死其他任务。

公平不等于延迟完全相同。1080p 与 4K 推理成本不同，任务优先级也可能不同。生产中可增加：

- 加权轮询：高优先级任务一轮获得更多配额。
- 输入分辨率限制：避免单路超大图像拖慢共享模型。
- 每任务最大 FPS：控制进入推理层的速率。
- 多 Worker 分片：按 GPU、租户或任务哈希分配。

### 29.3 最新值语义与队列语义

普通 FIFO 队列强调顺序和不丢数据，适合订单、账务和离线转码。实时监控强调“现在”，旧帧价值随时间快速下降，因此使用 Latest Value（最新值）语义：消费者开始工作时直接取最新帧并清理旧帧。

这种选择必须写进契约和指标，不能静默丢弃。若未来增加录像复盘或离线准确率评估，应建立另一条可回放链路，不能强迫实时告警链路同时承担逐帧完整性。

### 29.4 YOLO 三阶段耗时

一次检测可以拆成：

1. 预处理：BGR 图像缩放、补边、颜色/布局转换、归一化、生成 Tensor。
2. 推理：神经网络前向计算，通常是主要计算成本。
3. 后处理：解析输出、NMS 去重、置信度与类别过滤、坐标映射。

只记录总耗时无法定位优化方向。例如预处理慢可能是分辨率和内存拷贝问题；推理慢可考虑更小模型、GPU、FP16、ONNX/TensorRT；后处理慢可能是阈值过低导致候选框过多。

### 29.5 吞吐、延迟和 FPS 不能混为一谈

- 输入 FPS：视频源每秒产生多少帧。
- Capture FPS：系统每秒成功解码多少帧。
- Inference FPS：模型 Worker 忙碌时每秒处理多少帧。
- 端到端延迟：某一帧从捕获到检测完成等了多久。

吞吐高不保证延迟低。例如批量 16 帧可提高 GPU 吞吐，但第一帧必须等待批次凑齐。实时系统通常要在吞吐、延迟、显存和公平性之间取舍。

本项目的 `inference_fps = processed_frames / cumulative_processing_seconds`，不包含无帧空闲时间。它用于观察 Worker 能力，不代表任务在墙钟时间内实际收到的结果频率。短时样本容易受模型加载影响，正式报告必须注明样本长度、预热策略和设备。

### 29.6 P95 和冷启动

P95 表示约 95% 的观测值不超过该数值，比平均值更能暴露少数慢请求。窗口中只有 5 帧时，一次 4.8 秒冷启动就可能成为 P95；样本越少，分位数越不稳定。

需要分别观察：

- 冷启动延迟：进程首次加载模型、初始化后端和第一次推理。
- 预热后稳态延迟：模型已经驻留内存后的连续推理。
- 端到端尾延迟：包含排队、调度、绘框与系统抖动。

生产服务常在接流前执行预热，并用就绪探针区分“进程已启动”和“模型已可服务”。本项目当前保留真实冷启动数据，避免用预热结果掩盖启动成本。

### 29.7 锁粒度与慢操作

一把大锁虽然容易写，但会把无关操作串行化。模型加载、网络 I/O、视频解码和 JPEG 编码都可能很慢，不应在保护状态字典的锁中执行。

`InferenceWorker` 使用：

- `_lock`：快速读写任务缓冲映射、轮询队列、指标和最新结果。
- `_detector_lock`：保证并发情况下检测器只创建一次。

慢模型加载可以持有 `_detector_lock`，但状态 API 只需要 `_lock`，因此仍能返回“已注册但尚未产出结果”的快照。测试用一个阻塞工厂模拟慢加载，再从另一线程调用 `task_snapshot()` 验证锁粒度。

### 29.8 BGR、检测框和 JPEG

OpenCV 默认使用 BGR，而多数网页颜色和部分模型接口习惯 RGB。绿色在两种排列中都是 `(0, 255, 0)`，但红蓝会互换，调用其他 VLM/图像库前必须确认颜色空间。

检测框通常是浮点 `(x1, y1, x2, y2)`。绘制前要取整并裁剪到 `[0, width-1]`、`[0, height-1]`。在原图副本上画框，避免后续模块拿到被污染的像素。`cv2.imencode('.jpg', frame)` 在内存中编码 JPEG，适合 MJPEG 调试，不会自动保存到 MinIO。

### 29.9 环境变量布尔值为什么容易出错

操作系统环境变量全部是字符串。Python 中：

```python
bool("false") is True
bool("0") is True
```

因为非空字符串都是真。正确做法是去除空格、转小写，再匹配明确白名单。非法值应启动失败，而不是猜测：如果 `YOLO_HALF=fasle` 被静默当成真或假，问题会在模型运行时才暴露。

本项目 `_env_bool()` 接受 `true/false`、`1/0`、`yes/no`、`on/off`。测试还要注意 `get_settings()` 有模块级缓存：`monkeypatch` 恢复环境变量后，应再次 `reload_settings()` 清除被测试值构造的对象。

### 29.10 延迟加载与依赖注入

`InferenceWorker` 可接收现成 `detector`，也可接收 `detector_factory`，且二者必须恰好提供一个：

- 单元测试传 Fake Detector，不下载权重、不依赖 GPU。
- 真实运行传 Factory，第一帧到来时才加载 YOLO。

这叫依赖注入：核心调度只依赖“具有 `detect()` 的对象”，不负责知道 Ultralytics 的所有细节。它提升可测试性，也为以后替换 ONNX Runtime 或 TensorRT 留出边界。

### 29.11 检测预览请求全链路

```text
浏览器 <img src=".../detection-preview">
  → Flask 检查任务存在且 Runtime 已启动
  → RuntimeManager.latest_detection(task_id)
  → InferenceWorker 返回最新 InferenceResult
  → OpenCV 把 annotated_frame 编码为 JPEG
  → multipart 响应持续发送
  → 浏览器替换显示最新图片
```

若尚无检测结果，生成器短暂等待而不是重复发送同一帧；用 `frame_index` 去重。任务不存在返回 `404 TASK_NOT_FOUND`，存在但未启动返回 `409 RUNTIME_NOT_STARTED`。生产反向代理还需关闭响应缓冲，否则代理可能攒够数据后才一次发送，所以响应设置 `X-Accel-Buffering: no`。

### 29.13 常见面试追问

**为什么不每帧都交给 VLM？** VLM 延迟和成本远高于 YOLO。YOLO 负责高频感知，Tracker、ROI 和规则先筛出有变化的候选，再让 VLM 做低频语义理解。

**共享模型会不会成为单点瓶颈？** 会形成单 Worker 容量上限，但比每路复制模型更容易测量和扩容。通过任务分片、多 Worker、动态 batch 和设备级队列横向扩展，同时保留单 Worker 内公平性。

**为什么 P95 比当前单帧耗时高很多？** 端到端 P95 的短窗口包含首次模型加载；当前单帧 `inference_ms` 是稳态模型前向耗时。必须区分冷启动、模型耗时与端到端尾延迟。

**CPU 2.35 FPS 是否说明模型只能这么快？** 不能直接下结论。它来自 5 帧短时 Runtime 冒烟，包含首次加载影响和调度/绘框；完整预热基准是另一种测试。该结果只用于证明实时链路可运行和指标能采集。

**检测停止后为什么看不到最后指标？** 当前停止会注销内存状态，避免旧运行污染新 `run_id`。生产方案是在注销前把最终汇总持久化到 `TaskRun`，而不是无限保留 Worker 内存。


## 30. 前端 i18n、XHR 上传进度与 HLS 就绪轮询知识

本轮改动涉及若干"看似小其实每个都能被面试展开"的知识点，逐一拆开。

### 30.1 前端 i18n 的三种主流方案

| 方案 | 代表 | 适用规模 | 特点 |
|---|---|---|---|
| 声明式字典 | 自己写 200 行 | < 100 条词条 | 无依赖，`data-i18n` 属性绑定，切换时遍历 DOM |
| 运行时框架 | i18next / vue-i18n | 中大型 SPA | 支持插值、复数、命名空间、懒加载 |
| 构建期替换 | gettext / FormatJS | 静态站点 | 编译期把 key 换成语言字符串 |

我们选第一种，理由：页面数量少、词条少、要让 JS 文件在面试时能被完整讲透。

### 30.2 fetch vs XMLHttpRequest 的上传进度

- `fetch(url, { body: file })` 目前主流浏览器 **无法拿到上传阶段的进度事件**（下载阶段可以通过 `response.body` 的 ReadableStream 得到）；
- `XMLHttpRequest` 有独立的 `xhr.upload` 对象，可以监听 `progress`、`loadstart`、`load`、`error`、`abort`；
- 所以只要涉及"上传进度条"，标准答案就是 XHR。示例：

```js
const xhr = new XMLHttpRequest();
xhr.open('POST', '/api/upload');
xhr.upload.onprogress = e => {
  if (e.lengthComputable) bar.style.width = (e.loaded / e.total * 100) + '%';
};
xhr.onload = () => { /* 处理 xhr.responseText */ };
xhr.send(formData);
```

### 30.3 MJPEG 客户端重试策略

MJPEG 是"HTTP 长连接 + `multipart/x-mixed-replace`"，任何一次 502 都会让 `<img>` 触发 `onerror`。

常用重试策略：

1. **上限计数**（本项目采用）：连续错误 N 次后停止重试，避免死循环；
2. **递增退避**：500ms → 1500ms → 3000ms，减少雪崩；
3. **时间戳打破缓存**：`src = url + '?t=' + Date.now()`；
4. **用户可手动"重新连接"**：给按钮显式触发一次刷新。

### 30.4 UNIQUE 约束与"用户可见字段 vs 数据库唯一键"的解耦

一条常见的建模错误：让"用户直接输入的名字"同时充当数据库唯一键。改法有两种：

- **加后缀去唯一化**（本项目）：`unique_name = f"{filename} · {hex6}"`，简单直接；
- **拆列**：`display_name` 允许重复，`slug` 或 `uuid` 承担唯一约束。

面试展开时可以顺带聊：为什么 SQLAlchemy `IntegrityError` 会一路冒到 500——因为 `db.session.add + commit` 是同事务，异常在 commit 时抛出，Flask 未捕获就是 500；正确姿势是应用层预判或捕获重试。

### 30.5 时间等待：sleep vs 事件轮询 vs 事件驱动

启动一条依赖外部服务的流水线时，"要不要等"往往有三种做法：

| 做法 | 优点 | 缺点 | 场景 |
|---|---|---|---|
| `time.sleep(固定秒)` | 一行代码 | 太短会失败、太长又浪费 | Demo |
| 轮询就绪 endpoint | 简单、可控超时 | 有轻微 CPU 与网络开销 | 本项目 |
| 事件回调 / Webhook | 无轮询开销 | 需要目标服务主动推 | MediaMTX 无此能力 |

MediaMTX 没有"HLS ready"回调，所以我们选"轮询"。关键判据：

- 用 `time.monotonic()` 计时，避免 wall clock 跳变；
- 校验响应体首字节而不仅仅是状态码（MediaMTX 有时会先给 200 但 body 空）；
- 顺带检测 pusher 进程 `poll()`，任何一端挂了就立刻放弃，不再等超时。

### 30.6 `subprocess.Popen` 的生命周期检测

- `Popen.poll()` 返回 `None` 表示进程仍在运行；返回整数（Windows 上非零通常代表异常退出）表示已退出；
- `Popen.kill()` Windows 走 `TerminateProcess`，Linux 走 SIGKILL；
- 在 `/stop-pipeline` 里我们既要 `_ffmpeg_procs.pop`、又要 `kill`，两步是有序的：先 pop 再 kill 避免其他线程再次读到已死进程。

### 30.7 单元测试怎么 mock `urllib.request.urlopen`

要点：

- **在被测模块所在命名空间**打 patch：`patch("web.routes.monitor.urllib.request.urlopen")`，而不是 `urllib.request.urlopen`，因为 `import` 会在 monitor 模块里绑定别名；
- 返回值要支持上下文管理协议（`__enter__` / `__exit__`），因为源码用了 `with urllib.request.urlopen(...) as resp`；
- 用 `side_effect=[..., ..., resp]` 或函数计数器模拟"前两次失败第三次成功"；
- 断言"根本没调用 urlopen" 用 `mocked.assert_not_called()`。

### 30.8 面试时可能被追问的点

- Q：为什么不用 nginx 或者 HTMX？A：单页 + 少量交互，收益低于自己写一份可控的 XHR + 声明式 i18n。
- Q：`_wait_hls_ready` 死等 15s 会不会阻塞 Flask worker？A：会。生产上应改成异步任务（Celery / Redis 队列 / asyncio），本项目为演示保留同步 + 明确超时（15s）＋ 提前退出（进程早退）＋ 明确 504。
- Q：i18n 切换语言 SEO？A：`<html lang>` 也同步切换；如果要做 SSR，需要放到后端根据 `Accept-Language` 或 cookie 渲染，本项目不做。



## 31. 前端状态恢复、历史记录页与 MinIO 视频持久化知识

### 31.1 为什么页面刷新会"丢数据"

传统服务端渲染（SSR）页面每次刷新都是全新请求，JS 变量全部重置。现代 SPA 用路由切换避免刷新，但本项目是 Flask 多页应用，点击导航链接（`<a href="/monitor">`）会触发整页加载。

解决思路：
- **不改变多页架构**（对小白和面试都更清晰）；
- **用 localStorage 记住当前任务 ID**；
- **页面加载时从后端 rehydrate**（类似 SSR 的 hydration 概念）；
- **URL query `?task_id=xxx` 支持直接链接分享和恢复**。

### 31.2 localStorage vs sessionStorage vs Cookie

| 特性 | localStorage | sessionStorage | Cookie |
|---|---|---|---|
| 生命周期 | 永久（手动清除） | 标签页关闭 | 可设过期时间 |
| 容量 | ~5MB | ~5MB | ~4KB |
| 发送到服务器 | 否 | 否 | 每次 HTTP 请求自动携带 |
| 适用场景 | 用户偏好、最近任务 ID | 临时表单数据 | 会话认证 |

本项目用 `localStorage` 存 `currentTaskId`，因为：
1. 不需要发送给服务器（API 路径里已经有 task_id）；
2. 希望跨标签页持久化；
3. 数据量极小（一个整数）。

### 31.3 Jinja2 模板继承的 `{% block %}` 陷阱

Jinja2 的 `{% block %}` 是占位符，子模板填充内容。**块的位置决定了内容渲染到哪里**。

本项目踩的坑：
```html
<!-- base.html（错误写法） -->
<script>
    // 父页面的 JS 代码
    {% block extra_js %}{% endblock %}
</script>
```

子模板填充的 JS 代码会被嵌入到父页面的 `<script>` 标签内部，如果子模板内容也有 `<script>` 标签或特殊字符，就会导致语法错误。

正确做法：
```html
<!-- base.html（正确写法） -->
<script>
    // 父页面的 JS 代码
</script>
{% block extra_js %}{% endblock %}
```

子模板：
```html
{% block extra_js %}
<script>
    // 子页面独立的 JS 代码
</script>
{% endblock %}
```

**面试可讲**：模板继承的 block 是纯文本替换，不会自动处理 HTML 标签嵌套，开发者必须自己保证渲染后的 HTML 结构正确。

### 31.4 N+1 查询问题与批量聚合

**反模式（N+1）**：
```python
tasks = list_tasks()
for t in tasks:
    t.alarm_count = AlarmRecord.query.filter_by(task_id=t.id).count()
    # 每个任务一次 COUNT 查询 → 10 个任务 = 11 次 SQL
```

**正确做法（批量 IN 查询）**：
```python
task_ids = [t.id for t in tasks]
rows = db.session.query(
    AlarmRecord.task_id, func.count(AlarmRecord.id)
).filter(AlarmRecord.task_id.in_(task_ids)).group_by(AlarmRecord.task_id).all()
alarm_counts = dict(rows)
# 无论多少任务，始终 2 次 SQL
```

**面试可讲**：这是 ORM 最常见的性能陷阱，用 `IN + GROUP BY` 一次查询解决。

### 31.5 MinIO 对象存储核心概念

MinIO 是 S3 兼容的对象存储，核心概念：
- **Bucket**：顶层容器，类似磁盘分区；
- **Object**：文件 + 元数据，通过 `object_name`（key）访问；
- **Presigned URL**：带签名的临时下载链接，不需要暴露 AccessKey；
- **`fput_object` / `fget_object`**：文件路径方式上传/下载；
- **`put_object`**：流方式上传（适合小数据或分片）。

本项目 bucket 设计：
- `alarm-media`：告警截图、录像片段（原有的）
- `videos`：用户上传的原始视频文件（新增的）

**为什么视频不直接存 MySQL？**
1. MySQL BLOB 性能差，备份困难；
2. 视频文件大（100MB+），会撑大 binlog；
3. MinIO 天然支持大文件、分片上传、CDN 分发；
4. 数据库只存 URI（`videos/xxx.mp4`），轻量且可移植。

### 31.6 本地文件 + MinIO 双写策略

本项目采用"先本地、再 MinIO"的策略：
1. Flask 接收上传 → 先存 `data/videos/uploads/`（保证 FFmpeg 能立即读取）；
2. 异步/同步上传到 MinIO（持久化备份）；
3. `start-pipeline` 时检查本地文件是否存在，不存在则从 MinIO 下载。

**为什么不直接用 MinIO presigned URL 给 FFmpeg？**
- FFmpeg 对 S3 协议支持有限（需要编译时启用 libs3 或用 HTTP 范围请求）；
- presigned URL 有过期时间（默认 7 天），不适合长时间循环推流；
- 本地文件读取最稳定，零网络开销。

**生产演进方向**：
- 上传完成后删除本地文件（MinIO 作为唯一真源）；
- `start-pipeline` 时从 MinIO 下载到临时目录，分析完清理；
- 对大文件实现分片上传（Multipart Upload）和断点续传。

### 31.7 Flask 全局错误处理器

Flask 默认对未捕获异常返回 HTML 错误页（Werkzeug debug page 或 500 页面）。当前端用 `fetch().then(r => r.json())` 解析时，HTML 会导致 `Unexpected token '<'` 错误。

解决：注册全局 errorhandler，对 `/api/*` 路径返回 JSON：
```python
@app.errorhandler(Exception)
def _api_json_error(err):
    if not request.path.startswith("/api/"):
        raise err
    return jsonify({"success": False, "error": {...}}), 500
```

**关键设计**：非 API 路径（页面请求）仍然走 Flask 默认的 HTML 错误处理，只对 API 路径做 JSON 包装。

### 31.8 数据库迁移：Alembic 自动检测的局限

Flask-Migrate（Alembic）的 `flask db migrate` 能自动检测模型变化，但有时会报告"No changes in schema detected"，原因可能是：
1. SQLAlchemy 模型没有正确 import（Alembic 的 `target_metadata` 没看到新字段）；
2. 字段类型在数据库和模型间的差异不够明显；
3. BOM 头（U+FEFF）导致 Python 文件解析异常。

本项目选择手动编写迁移脚本（`add_storage_uri.py`），因为：
- 自动生成可能遗漏索引或注释；
- 手动写更可控，面试时能讲清楚 upgrade/downgrade 逻辑；
- 一个 ALTER TABLE ADD COLUMN 语句非常简单。

### 31.9 SQLAlchemy `Optional` 列与 Python `None`

`Column(String(500), default="")` 和 `Column(String(500), nullable=True)` 的区别：
- `default=""` 是 Python 端默认值，INSERT 时如果没传值，SQLAlchemy 会填入空字符串；
- `nullable=True` 是数据库端约束，允许 NULL；
- 从数据库读出 NULL 时，Python 端得到 `None`，不是空字符串。

本项目 `storage_uri` 用 `default=""` 是为了前端简化判断（空字符串和 None 都表示"无 MinIO 对象"），但在 API 响应中仍然返回 `None`（因为旧数据可能是 NULL）。
