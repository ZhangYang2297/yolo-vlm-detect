一、项目概述
1.1 系统简介
AI视频数据分析系统是一套基于「大小模型协同」架构的智能视频分析平台。系统采用 YOLO 小模型进行实时目标检测与跟踪，配合 VLM（Vision Language Model）大模型进行语义级行为判定与深度分析，实现对视频流、图片、视频文件的全方位智能监控与告警。
1.2 核心设计理念
● 大小模型协同：YOLO 负责高速目标检测与追踪（帧级别），VLM 负责语义理解与行为判定（秒级别），两者分工明确，兼顾实时性与准确性
● 多进程解耦架构：Producer（生产者）、Consumer（消费者）、Saver（持久化）三个核心进程通过 Redis 消息队列解耦，独立部署、独立扩缩容
● RAG 增强规范审查：支持上传行业规范文档（如 GB30871-2022），通过向量检索自动将相关规范注入 VLM 提示词，实现基于法规的智能合规检测
● 热更新零停机：配置修改、模型替换、任务参数调整均可通过 Redis Pub/Sub 实时通知各进程热重载，无需手动重启
1.3 技术栈
层面	技术选型
Web 框架	Flask + Jinja2 模板 + Bootstrap 5
数据库	MySQL 5.7+ (SQLAlchemy ORM)
消息队列	Redis (列表队列 + Pub/Sub)
对象存储	MinIO (S3 兼容协议)
流媒体服务	MediaMTX (RTSP/WebRTC/HLS)
目标检测	Ultralytics YOLO (v8/v11/v26) + PyTorch
视频处理	PyAV (FFmpeg) + OpenCV
大语言模型	OpenAI 兼容协议 (vLLM/Qwen 等)
向量数据库	ChromaDB + sentence-transformers
GPU 加速	CUDA (推理) + NVENC (编码推流)

2.2 核心进程说明
Producer（生产者 — ai/producer.py）
● 职责：从视频源拉流 → YOLO 目标检测 → 目标跟踪 (BotSort) → 区域过滤 → 裁剪/全帧截图 → 通过 Redis 队列投递给 Consumer → 实时推流到 MediaMTX
● 运行方式：每个视频源独立进程，支持多任务共享同一路视频流
● 关键特性：
  ○ 支持 GPU 批推理（YOLO_INFER_BATCH_SIZE）
  ○ 支持 NVENC 硬件编码推流
  ○ 动态追赶机制：实时流延迟超过阈值自动跳帧追赶
  ○ 多种分析模式：small_only、small_crop、small_full、large_only、temporal
  ○ 告警视频录制：环形缓冲区前后各 5 秒共 10 秒视频
  ○ Redis Pub/Sub 热更新：配置变更后自动重启
Consumer（消费者 — ai/consumer.py）
● 职责：从 Redis 队列取出 VLM 任务 → 调用大模型推理 → 解析判定结果 → 写回 Redis
● 运行方式：多进程 × 多线程架构（Supervisor 进程管理）
  ○ CONSUMER_WORKERS 个工作进程（进程级隔离）
  ○ 每个进程 CONSUMER_THREADS_PER_WORKER 个并发线程
● 关键特性：
  ○ 多端点负载均衡：Round-Robin 轮询多个 VLM 端点
  ○ 动态降级保护：排队延迟超过 15s 自动关闭思考链，进入极速分类模式
  ○ 巡检模式：强制深度思考，输出完整分析报告
  ○ 时序分析模式：将多帧序列投递给大模型进行时序动作识别
  ○ RAG 规范注入：检索相关安全规范规则自动注入 system prompt
  ○ 思考流分离：兼容 vLLM 原生 reasoning_content 和 <think> 标签两种格式
  ○ JSON 解析容错：正则兜底、字段兜底、纯文本关键词匹配三级降级
Saver（持久化 — ai/saver.py）
● 职责：从 Redis 告警队列取出告警数据 → 上传截图/视频到 MinIO → 写入 MySQL → 触发第三方推送
● 关键特性：
  ○ 连接池数据库操作（PooledDB）
  ○ 时序模式支持多帧上传 + 九宫格缩略图拼接
  ○ 告警视频 MP4 上传
  ○ 推送模块：异步线程池执行 HTTP POST 推送，含冷却防重复机制
  ○ 支持 Redis Pub/Sub 参数热重载
2.3 数据流转
视频源 → Producer[YOLO检测+跟踪]
              ↓ (base64截图 + 元数据)
         Redis: vlm_task_queue
              ↓
         Consumer[VLM推理]
              ↓ (判定结果)
         Redis: vlm_result:{task_id}
              ↓ (Producer 轮询读取)
         Producer[命中判定+告警触发]
              ↓ (告警数据)
         Redis: alarm_save_queue
              ↓
         Saver[MinIO上传 + MySQL写入 + HTTP推送]

参数	类型	说明

十五、推流与实时预览
15.1 推流机制
Producer 进程中的 FFmpegStreamPusher 类负责将处理后的视频画面推流到 MediaMTX：
特性	说明
异步非阻塞	主线程只投递最新帧，后台线程负责编码推流
帧队列	固定容量队列（默认 2 帧），满时丢弃旧帧保持实时性
GPU 编码	优先使用 NVENC 硬件编码器，不可用时降级 libx264
自动重连	FFmpeg 进程异常退出后自动重启
缩放支持	通过 PUSH_STREAM_SCALE 配置输出分辨率缩放比例
预设配置	通过 PUSH_STREAM_PRESET 配置编码质量/速度预设
15.2 画面标注
推流画面上叠加的信息：
● 检测区域（ROI）边界线
● 目标检测框（绿色/橙色/红色表示不同状态）
● 目标 ID 编号
● VLM 确认的告警文字高亮（红色粗框 + 中文标签）
● 告警信息顶部半透明条幅
● 中文字体渲染使用 PIL + SimSun

十六、告警录像功能
16.1 功能说明
开启 is_record_video 后，告警触发时自动录制环形缓冲区中的前后各 5 秒（共约 10 秒）视频片段，以 MP4 格式上传到 MinIO。
16.2 数据流
视频帧 → 环形缓冲区（持续缓存最近 N 秒帧）
          ↓ 告警触发
截取缓冲区前 5 秒帧 + 继续录制后 5 秒帧
          ↓
FFmpeg 编码为 MP4
          ↓
base64 编码 → 通过 Redis alarm_save_queue 送入 Saver
          ↓
Saver 上传 MP4 到 MinIO → video_clip_url 写入 alarm_record

十七、时序分析模式
17.1 功能说明
时序分析模式（temporal）适用于需要连续多帧综合判断的场景（如动作识别、趋势分析）：
1. Producer 在时间窗口（temporal_window_seconds，默认 5 秒）内按等间隔采样 temporal_frames_count（默认 8 帧）
2. 所有帧一次性投递给 Consumer
3. Consumer 将多帧按时间顺序构建为多 image_url 消息，一次性发送给 VLM
4. VLM 综合多帧画面进行时序分析
5. 告警时的 Saver 会上传所有帧并生成九宫格缩略图

十八、巡检模式
18.1 功能说明
当 target_actions 为空时，任务进入巡检模式（inspection_mode）：
● 每次 VLM 分析都会落盘为告警记录
● 强制启用深度思考（enable_thinking=True）
● 输出完整的分析报告（包含思考过程 + 分析结论）
● 适用于设备巡检、环境监测等需要全面记录的场景
● 最大输出 token 数提升至 8192
