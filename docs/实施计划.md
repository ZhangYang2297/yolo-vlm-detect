# AI视频智能分析系统 实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 从零开发一套基于YOLO+VLM大小模型协同的多模态（视频+音频）智能分析系统，生产级技术栈（MySQL+MinIO+Chroma），适配RTX 4050笔记本，具备推理加速和完善可观测性，作为秋招AI大模型岗位的高含金量展示项目。

**Architecture:** 三进程解耦架构：Producer负责拉流/YOLO检测/音频采集、Consumer负责VLM语义推理/音频分析、Saver负责MinIO持久化/MySQL落盘/告警推送。三进程通过Redis消息队列解耦，支持独立扩缩容。内置MJPEG实时推流浏览器原生播放。支持音频异响检测（两级分析架构）。支持RAG法规增强（Chroma向量库+行业规范注入）。支持YOLO ONNX/FP16推理加速。Prometheus指标+Grafana风格Web监控大盘。

**Tech Stack:** 
- Web: Flask + Bootstrap 5 + Jinja2 + Server-Sent Events
- 数据库: MySQL 8.0+ (SQLAlchemy ORM)
- 消息队列: Redis 7.0+ (列表队列 + Pub/Sub热更新 + 缓存)
- 对象存储: MinIO (S3兼容协议，存储截图/录像/音频)
- 流媒体: MediaMTX (RTSP推流+WebRTC播放，企业标准方案，支持NVENC硬件编码)
- 目标检测: Ultralytics YOLOv8s + ONNX Runtime GPU + FP16半精度
- 视频处理: OpenCV + PyAV (FFmpeg)
- 音频处理: librosa + pydub + VLM音频多模态理解
- 大语言模型: OpenAI兼容协议（云端GPT-4o-mini / 本地Qwen2-VL-2B/7B-AWQ量化）
- 向量数据库: ChromaDB (嵌入式、持久化、元数据过滤，适合万级文档规模)
- 可观测性: prometheus_flask_exporter + structlog JSON日志
- GPU加速: CUDA + ONNX Runtime + FP16 + AWQ量化（本地VLM）
- 部署: Waitress(Windows)/Gunicorn(Linux) 生产级WSGI服务器

## Global Constraints

- **运行环境:** RTX 4050笔记本（6GB显存），Windows/Linux兼容
- **模型选择:** 优先使用开源预训练权重，不从头训练：
  - YOLOv8s.pt（COCO预训练，人/车/常见物体检测）

  - 本地VLM（可选）：Qwen2-VL-2B-Instruct-AWQ（~2GB显存）或Qwen2-VL-7B-Instruct-AWQ（~4GB显存）
  - 云端VLM：GPT-4o-mini / Qwen-VL-Max API
- **依赖约束:** 除Redis/MySQL/MinIO三个外部服务，其余均为Python嵌入式组件

- **测试约束:** 核心模块必须有单元测试，每个阶段完成后可独立运行验证
- **配置管理:** 环境变量 + `.env` + yaml 三级覆盖，支持Redis Pub/Sub热更新

### Task 4: YOLO检测器封装（ONNX+FP16加速+ByteTrack）

**Files:**
- Create: `ai/yolo_detector.py`
- Create: `ai/prompt_templates.py`
- Test: `tests/test_yolo.py`

**Interfaces:**
- Produces: Detection dataclass: bbox(x1,y1,x2,y2), class_id, class_name, confidence, track_id
- Produces: YOLODetector类：
  - `__init__(model, device, confidence, iou, classes, use_onnx, use_half)`
  - `detect(frame) -> list[Detection]` 单帧检测
  - `track(frame, persist=True) -> list[Detection]` 带ByteTrack跟踪
  - `export_onnx()` 导出ONNX模型

**推理加速实现（RTX 4050优化）：**
1. **ONNX Runtime GPU导出与推理**：首次启动自动导出，推理速度比原生PyTorch快20-30%
2. **FP16半精度**：device=cuda时启用，显存减半速度提升约40%
3. **预训练权重切换**：默认用yolov8s.pt（比n精度高mAP高约5个点），安全帽检测用开源`hard_hat_workers`预训练权重
4. **批推理支持**：batch_size>1时批量推理提升吞吐
5. **类别过滤**：推理前传入classes参数，只计算需要的类别，减少后处理开销

**提示词模板设计（模块化、可组合）：**
- `SYSTEM_PROMPT_BASE`：通用系统提示，规定JSON输出格式和分析原则
- `build_prompt(scene_desc, target_actions, rules_context, is_temporal)`：动态构建user prompt
- `build_audio_prompt(scene_desc)`：音频分析专用提示词
- `build_inspection_prompt()`：巡检模式深度分析提示词（启用thinking，输出更详细）
- 核心原则：**输出强制JSON格式，要求置信度分数，低于0.6判定正常，幻觉防控**

### Task 6: 音频分析模块（多模态两级检测架构）

**Files:**
- Create: `ai/audio_analyzer.py`
- Test: `tests/test_audio.py`

**Interfaces:**

- Produces: AudioAnalyzer类：

  - `_calculate_rms_energy()` / `_analyze_spectrum()` 特征初筛
  - 支持的异常声音：爆炸/撞击、玻璃破碎、尖叫/呼救、警报器、剧烈争吵

**两级检测架构设计（核心亮点）：**
```
音频帧 → 轻量特征初筛（CPU实时，<10ms）
           ├─ 静音/低能量 → 直接返回正常，不调用VLM
           ├─ 高能量+高频特征 → 疑似异常，保存WAV片段
           └─ 疑似异常 → VLM多模态精确分类（去误报）→ 最终结果
```
**为什么这么设计？** 99%的音频是正常声音或静音，直接全部喂给VLM：延迟高（几秒）、成本高（音频token贵）、GPU占用大。两级架构用CPU轻量模型过滤掉绝大多数无效请求，只有<5%的疑似片段才调用VLM确认，兼顾实时性、成本和准确率。

**音频源处理：**
- 本地视频文件：用PyAV提取音频轨道，按chunk_duration切片
- RTSP流：用FFmpeg拉取音频轨，实时处理
- 后续扩展：支持独立麦克风输入

### Task 7: Producer生产者进程

**Files:**
- Create: `ai/producer.py`

**Interfaces:**
- Produces: MJPEGStreamer类：线程安全帧缓存，`get_frame(source_id) -> bytes` 返回JPEG
- Produces: RingBuffer类：环形缓冲区缓存前后5秒帧，用于告警录像
- Produces: VideoProducer类：
  - `run()` 主循环：拉流→检测→跟踪→ROI过滤→VLM任务投递→MJPEG推流
  - 支持视频文件/RTSP流/摄像头ID三种源
  - 三种分析模式：small_crop/small_full/temporal

**核心功能点：**
1. **OpenCV/PyAV拉流**：视频文件循环播放或结束退出，RTSP断开自动重连（3秒间隔）
2. **YOLO目标跟踪**：每帧跑track()，同一目标稳定ID，跨帧轨迹关联
3. **ROI多边形过滤**：配置多边形区域，目标中心点在区域内才触发分析
4. **画框标注**：检测框颜色区分（绿色正常/红色告警）、目标ID、ROI边界、FPS叠加
5. **RTSP推流到MediaMTX**：FFmpeg子进程（优先NVENC硬件编码，降级libx264）将画好框的帧编码为H.264，推RTSP到MediaMTX的`rtsp://localhost:8554/task_{id}`路径
6. **前端WebRTC播放**：通过MediaMTX的WebRTC端口8889拉流，浏览器低延迟预览（<500ms），支持音频
6. **VLM任务节流**：vlm_interval秒一次，相同track_id目标不重复发送（去重逻辑）
7. **时序分析模式**：temporal_window秒内等间隔采样temporal_frames帧，一次性投递给VLM做多帧动作理解（摔倒/打架等连续性行为）
8. **环形缓冲区**：持续缓存最近5秒帧，告警触发时截取前5秒+后5秒编码为MP4存MinIO
9. **热更新监听**：订阅Redis `task:{id}:update` 频道，收到消息优雅重启加载新配置
10. **延迟追赶机制**：处理速度跟不上实时流时自动跳帧，避免队列积压导致延迟越来越大

- 万级规则规模性能足够，这个项目用完全没问题

3. 每个分块调用VLM提取规则：prompt要求只提取"可以通过监控画面视觉判断的规则"，过滤掉纯管理类条款
4. 提取的规则包含：条款号、标题、违规描述、视觉特征、检测建议
5. 用sentence-transformers编码写入Chroma，元数据包含doc_id/clause/enabled等字段
