## 2. 项目定位与总体架构
`
### 2.1 要解决的问题
`
项目目标不是“对一张图调用一次大模型”，而是构建一条可持续运行的视频智能分析链路：接入视频和音频，先用轻量模型筛选值得分析的片段，再调用 VLM 理解行为，把证据、告警和指标保存并展示。
`
典型场景可选“园区/工厂安全巡检”：人员闯入、未佩戴安全装备、吸烟、跌倒、明火、异常声音等。这个场景比泛化“识别人的行为”更容易定义规则、收集数据和量化效果。
`
### 2.2 统一目标架构
`
```	ext
视频源 → MediaMTX → Capture Worker → Inference Worker（集中加载YOLO）
                                      ↓
                               Event Producer
                                      ↓
                            Redis Candidate Stream
                                      ↓
                              VLM Consumer + RAG
                                      ↓
                             Redis Result Stream
                                      ↓
                         Saver → MySQL + MinIO + SSE
```
`
这种拆分比旧的“Producer同时拉流、YOLO、音频”更清晰：Capture只处理媒体，Inference集中加载一次模型，Event Producer只决定何时值得调用VLM。这样可以避免每个视频源重复占用模型内存，也便于分别测试解码、推理、触发和语义分析。
`

| Web 管理层 | 已实现 | 任务/告警 API、基础页面、SSE 入口 |
| 推流 | 部分实现 | 本地 RTSP 发布/拉流、OpenCV 取帧和 HLS 解码已验证；WebRTC 仅验证页面入口 |

## 3. Docker 基础设施模块【已实现】
`
### 3.1 作用
`
`docker-compose.yml` 用一条命令启动四个独立服务，避免在 Windows 上逐个安装、配置和卸载。应用本身目前在宿主机 Python 中运行，基础服务在容器中运行。
`
### 3.2 为什么选择这些组件
`
| 组件 | 选择原因 | 没选更重方案的原因 |
|---|---|---|
| Redis 7 | 队列、缓存、事件通知一体；学习成本低 | Kafka/RabbitMQ 运维更重，单笔记本阶段收益小 |
| MySQL 8.4 | 企业常见、关系和事务适合任务/告警 | SQLite 并发和生产代表性较弱 |
| MinIO | S3 兼容，适合截图、录像、音频等大文件 | 不把大二进制塞 MySQL；本地文件难扩展与授权 |
| MediaMTX | 单二进制支持 RTSP/HLS/WebRTC，配置轻 | 自己搭转码服务器复杂；仅 MJPEG 延迟和带宽能力有限 |
`
### 3.3 Compose 关键配置
`
- `image`：从镜像创建容器的模板。
- `container_name`：固定容器名，便于 `docker logs` 和 `docker exec`。
- `ports`：`宿主机端口:容器端口`。MySQL 用 `3307:3306` 避开本机 MySQL 9.1。
- `volumes`：保存 Redis、MySQL、MinIO 数据；删容器后数据卷仍在。
- `restart: unless-stopped`：Docker 重启后自动恢复，除非用户明确停止。
- `command`：Redis 打开 AOF；MySQL 使用 `utf8mb4`；MinIO 同时开放 API 和控制台。
`
### 3.4 开发过程
`
1. 写 Compose 服务定义和端口。
2. 添加 named volume，避免容器重建丢数据。
3. 将 MediaMTX 配置文件挂载到容器。
4. `docker compose up -d` 后逐个做协议级健康检查，而不是只看容器为 Up。
5. 发现宿主机 `3306` 冲突后，将 Docker MySQL 宿主端口调整为 `3307`。
6. 为 MediaMTX 显式开放 `pedestrian` 发布路径，使用 45 秒行人片段完成真实链路补测。
`
### 3.5 风险和改进
`
- 当前 Compose 中是开发默认口令，生产必须使用 `.env`/Docker Secret 注入，不提交真实 secret。
- Redis 当前无密码，端口只能绑定本机或受防火墙保护。
- `latest` 镜像不可复现，应固定 MinIO、MediaMTX 的明确版本。
- `depends_on` 只控制启动顺序，不代表服务 ready；未来加入 `healthcheck`。
- 定期备份 MySQL 与 MinIO，验证恢复流程。
`
## 4. 配置管理模块【已实现】
`
### 4.1 文件
`
- `config/default.yaml`：非敏感默认业务参数。
- `config/settings.py`：Pydantic 配置模型、YAML 加载、环境变量覆盖和单例缓存。
- `.env.example`：变量模板；实际 `.env` 不应提交。
`
### 4.2 为什么这样设计
`
代码里写死配置会导致换机器、换端口、换模型时修改源码。这里采用“默认值 < YAML < 环境变量”的思路：公共参数进 YAML，密码/API Key 进环境变量，Pydantic 负责类型转换和结构化访问。
`
### 4.3 核心流程
`
1. `load_dotenv()` 将本地 `.env` 加载到进程环境。
2. `_load_yaml()` 读取 `config/default.yaml`，不存在时返回空字典。
3. `get_settings()` 构造 `Settings`，关键基础设施参数优先读取 `os.getenv()`。
4. `_settings` 缓存结果，避免每次调用都读磁盘。
5. `reload_settings()` 清空缓存，主要用于测试或运行时重载。
`
### 4.4 当前配置组
`
`FlaskConfig`、`MysqlConfig`、`RedisConfig`、`MinioConfig`、`MediaMTXConfig`、`YoloConfig`、`VlmConfig`、`QueueConfig`、`AnalysisConfig`、`AudioConfig`、`ChromaConfig`、`ObservabilityConfig`、`StorageConfig`。
`
### 4.5 注意点
`
- Pydantic 能校验类型，但当前字段缺少范围约束，例如置信度应为 0～1、端口应为 1～65535。
- `get_settings()` 是进程内单例；修改 `.env` 后需重启或显式 reload。
- 当前 `.env.example` 带开发默认口令，仅用于本机示例，不能复制到生产。
- `default.yaml` 中存在尚未实现模块的配置，不等于功能已完成。
`
## 5. Flask 应用工厂【已实现】
`
### 5.1 文件与入口
`
`app.py` 的 `create_app(register_metrics=True)` 创建 Flask 应用，初始化数据库、CORS、Prometheus、Blueprint、SSE 和健康检查。模块末尾 `app = create_app()` 方便 WSGI Server 导入。
`
### 5.2 为什么使用应用工厂
`
应用工厂让测试可以创建独立 app，也方便未来提供开发、测试、生产不同配置。直接在全局堆初始化代码，会导致测试导入时难以控制副作用。
`
### 5.3 启动流程
`
1. 创建 Flask 实例并指定模板/静态目录。
2. 设置 `SECRET_KEY` 和 200 MB 上传上限。
3. 初始化 CORS 和 SQLAlchemy，并自动建表。
4. 注册 Prometheus exporter；全局 `_metrics` 防止重复注册。
5. 注册页面 Blueprint 和 `/api` Blueprint。
6. 创建 Chroma 持久化目录。
7. 注册 `/events` SSE 和 `/health`。
8. 开发模式使用 Flask server，其他模式在 Windows 使用 8 线程 Waitress。
`
### 5.4 SSE 事件流
`
`/events` 订阅 Redis `alarm:new`，每收到消息就输出 `data: ...\n\n`。SSE 是服务器到浏览器的单向长连接，适合告警通知，比轮询及时且比 WebSocket 简单。
`
当前问题：每个 SSE 客户端长期占用线程；Redis 断连没有重连；没有心跳、鉴权和客户端数限制。规模扩大后应使用异步网关或专门推送服务。
`
### 5.5 安全与生产问题
`
- `CORS(app)` 当前允许所有来源；生产应只允许可信前端域名。
- 无登录和权限，任何访问者都能删除/启停任务。
- 开发 server 不能用于生产；Windows 使用 Waitress，Linux 可用 Gunicorn。
- `/health` 只证明 Web 进程活着，不证明 Redis/MySQL/MinIO ready；未来拆分 liveness/readiness。
`
## 6. MySQL 与 ORM 模块【已实现】
`
### 6.1 文件
`
- `core/db.py`：连接 URI、连接池和建表。
- `core/models.py`：五张业务表和 ORM 关系。
`
### 6.2 为什么 MySQL + SQLAlchemy
`
任务、告警、规则之间有明确关系，需要事务、外键和查询；MySQL 是常见企业数据库。SQLAlchemy 把 Python 对象映射为表，提供参数化 SQL，减少手拼 SQL 和注入风险，但仍需理解索引与事务。
`
### 6.3 连接设计
`
URI 使用 `mysql+pymysql://...?...charset=utf8mb4`。连接池参数：
`
- `pool_size=10`：每进程维护最多 10 个基础连接。
- `pool_recycle=3600`：定期回收，避免 MySQL 长连接过期。
- `pool_pre_ping=True`：取连接前检查，降低“server has gone away”。
`
多进程部署时每个进程都有自己的连接池，例如 4 进程理论上可产生约 40 个基础连接，必须与 MySQL `max_connections` 一起规划。
`
### 6.4 表职责
`
| 表 | 作用 | 状态 |
|---|---|---|
| `analysis_tasks` | 视频源、检测类别、ROI、音频开关、分析模式 | 已用于 API |
| `alarm_records` | 告警文本、置信度、证据 object key、复核状态 | 已用于 API |
| `rule_documents` | 规范 PDF 元数据和解析状态 | 仅建模 |
| `extracted_rules` | 从规范提取的视觉规则及 Chroma ID | 仅建模 |
| `system_metrics` | 系统指标历史记录 | 仅建模 |
`
`AnalysisTask.alarms` 设置 `cascade="all, delete-orphan"`，删除任务时关联告警会被 ORM 级联删除。外键也声明 `ON DELETE CASCADE`，但实际数据库行为仍需确认 MySQL 引擎与迁移结果。
`
### 6.5 事务与异常
`
当前接口执行 `add → commit`，没有统一捕获 `IntegrityError` 并 rollback。如果提交失败而不 rollback，该 session 后续操作会继续失败。后续应增加 service 层和统一事务边界。
`
### 6.6 表结构改进
`
- 用 Alembic/Flask-Migrate 管理版本；`create_all()` 不会修改既有表结构。
- JSON 默认值建议用 callable，例如 `default=list`，避免可变默认值语义问题。
- 为常用组合查询增加索引，如 `(task_id, created_at)`、`(status, created_at)`。
- 对枚举字段做应用层与数据库层约束。
- 大数据量分页改为基于 `created_at,id` 的游标分页。
`
## 7. Redis 模块【已实现】
`
### 7.1 文件与能力
`
`core/redis_client.py` 提供：
`
- `get_redis()`：懒加载连接池客户端并 `ping`。
- `enqueue()` / `dequeue()`：Redis List 队列。
- `set_result()` / `get_result()`：带 TTL 的 JSON 缓存。
- `publish()` / `subscribe()`：事件通知。
- `get_queue_size()`：积压长度和 Dashboard 指标。
`
### 7.2 队列如何工作
`
生产者用 `RPUSH` 把消息放列表右侧，消费者用 `BLPOP` 从左侧阻塞读取，因此保持 FIFO。`timeout=1` 让消费者定期醒来，可以检查停止信号，而不是永久卡死。
`
### 7.3 序列化和 TTL
`
Python dict 通过 `json.dumps(..., ensure_ascii=False, default=str)` 转成字符串，中文不转义。结果缓存使用 `SET ... EX ttl`，写值与设置过期时间在一条 Redis 命令中完成。
`
### 7.4 并发与可靠性
`
Redis 单条 List 命令是原子的，10 线程并发写 200 条测试没有丢失。但 `BLPOP` 取走后消息立即从队列消失，如果消费者处理到一半崩溃，消息无法自动恢复。
`
阶段二原型可继续 List；准备展示可靠性时建议升级：
`
1. Redis Streams + Consumer Group。
2. 消息包含 `message_id`、`task_id`、`attempt`、`created_at`。
3. 消费成功后 ACK；超时消息重新认领。
4. 达到重试上限进入死信流。
5. Saver 按业务幂等键去重，避免重复告警。
`
### 7.5 Pub/Sub 限制
`
Pub/Sub 不持久化，订阅者离线时消息丢失。因此适合“刷新页面”通知，不适合承载必须处理的告警任务。可靠业务事件应进 Stream/List，Pub/Sub 只做实时提示。
`
## 8. MinIO 对象存储模块【基础能力已实现，生产增强待开发】
`
### 8.1 为什么不用 MySQL 存文件
`
截图、录像和音频体积大，放数据库会让备份、查询和网络开销变重。MySQL 只存 object key，MinIO 保存二进制内容，这是“元数据与对象分离”。
`
### 8.2 文件与接口
`
`core/minio_client.py` 懒加载 MinIO 客户端，首次连接检查 bucket，不存在则创建。提供字节上传、文件上传、预签名下载 URL 和对象存在性检查。
`
### 8.3 Object key 规范
`
建议：
`
```	ext
alarms/{task_id}/{yyyy}/{mm}/{dd}/{alarm_id}/image.jpg
alarms/{task_id}/{yyyy}/{mm}/{dd}/{alarm_id}/clip.mp4
alarms/{task_id}/{yyyy}/{mm}/{dd}/{alarm_id}/audio.wav
rules/{document_id}/{md5}.pdf
```
`
key 要稳定、可追踪、避免用户原始文件名直接参与路径。MySQL 只保存 key，不保存带时效签名的 URL。
`
### 8.4 异常与一致性
`
上传失败返回 `None` 并写日志。后续 Saver 必须处理跨系统一致性：先上传临时 key，再写数据库，成功后标记完成；失败要重试或清理孤儿对象。MySQL 事务无法直接覆盖 MinIO。
`
### 8.5 安全
`
- bucket 保持私有，通过短期 presigned URL 访问。
- 当前默认 7 天可能过长，告警证据可按权限缩短到分钟级。
- 上传要限制大小、MIME、扩展名并检查实际文件头。
- 生产启用 TLS、最小权限 access key、生命周期清理和访问审计。
`
### 8.6 后续开发边界与顺序
`
当前代码只是最小封装，不包含完整文件管理系统。后续已经纳入实施计划，按以下顺序开发：
`
1. **Saver闭环阶段（P0）**：补单对象删除、批量删除、重试、SHA-256、统一key、软删除、Cleaner Worker、孤儿对象扫描和指标。
2. **离线视频上传阶段（P1）**：实现浏览器直传MinIO的Multipart断点续传，保存`upload_id`、`part_number`和`ETag`，支持暂停、刷新恢复、完成与中止。
3. **生产安全阶段（P0/P1）**：先做私有Bucket、15分钟签名URL、TLS和最小权限，再按环境启用SSE-S3或SSE-KMS。
4. **暂不首版实现**：客户端AES-GCM加密。它会让浏览器预览、FFmpeg读取和服务端分析都必须先解密，复杂度和收益暂不匹配单机秋招项目。
`
需要区分两个概念：`MinioStorage.upload_file()`底层调用`fput_object()`时，SDK会流式读取并可能自动使用Multipart，能够避免一次把大文件读入内存；但它没有保存前端上传会话和已完成分片，因此不等于“浏览器断网后刷新页面还能继续”的业务级断点续传。
`
### 8.7 删除为什么采用最终一致性
`
MySQL事务不能回滚MinIO操作。若先删数据库再删对象，MinIO失败会留下孤儿文件；若先删对象再删数据库，数据库失败会留下断链记录。因此首版采用：
`
```	ext
用户请求删除
→ MySQL标记deleting/软删除
→ Redis投递清理任务
→ Cleaner删除MinIO对象（可重试、幂等）
→ 成功后更新deleted状态
→ 多次失败进入死信并告警
```
`
批量删除必须返回每个object key的结果。对象不存在可按幂等成功处理；权限不足、网络失败和服务端错误必须保留失败原因并重试，不能用一个布尔值掩盖部分失败。
`
## 9. 结构化日志模块【已实现】
`
`core/logger.py` 使用 structlog。开发环境输出彩色可读日志，非开发环境输出 JSON，便于日志平台按 `event`、`queue`、`object`、`error` 等字段检索。
`
日志应回答“什么时候、哪个任务、在哪个阶段、耗时多久、为什么失败”。后续统一绑定 `request_id`、`task_id`、`trace_id`、`message_id`，异常使用 `logger.exception` 保留堆栈。密码、API Key、签名 URL、原始敏感画面不能写日志。
`
## 10. Prometheus 指标模块【已实现骨架】
`
### 10.1 文件与指标类型
`
`core/metrics.py` 预定义 YOLO、VLM、音频、队列、告警、进程和系统指标。
`
- `Counter`：只增不减，例如请求总数、丢帧数。
- `Gauge`：可增可减，例如队列长度、显存。
- `Histogram`：把耗时放入 buckets，可计算 P95/P99。
- `Info`：版本和环境等静态信息。
`
### 10.2 当前使用情况
`
Redis 入队、出队和队列长度已更新指标；Flask exporter 暴露 `/metrics`。YOLO、VLM、音频指标目前只是定义，相关业务尚未实现。
`
### 10.3 设计原则
`
标签不能使用 `task_id`、URL、错误全文等高基数字段，否则 Prometheus 时序数量爆炸。适合标签的是模型名、状态、设备类型、告警级别等有限集合。
`

### 11.1 路由清单
`

## 16. VLM 行为理解【后续设计】
`
### 16.1 输入策略
`
向 VLM 发送“局部目标裁剪 + 一张缩放全景 + 场景/规则文本”，兼顾人物细节和上下文。时序行为如跌倒、打斗需多帧，单帧无法可靠判断动作过程。
`
### 16.2 结构化输出
`
要求模型输出固定 JSON：`has_violation`、`behaviors`、`severity`、`confidence`、`evidence`、`reason`。响应必须用 Pydantic 校验，失败时修复/重试，不能直接信任自然语言。
`
### 16.3 生产策略
`
- 超时、指数退避、429/5xx 分类重试。
- 并发 semaphore，防止瞬间耗尽 API 配额和显存。
- pHash/embedding 缓存相似画面，但缓存键必须包含规则和 Prompt 版本。
- 熔断与降级：VLM 不可用时保留 YOLO 候选并标记待补偿。
- 防 Prompt 注入：外部规范和 OCR 文本作为不可信数据，不允许覆盖系统约束。

## 17. 音频分析【后置设计】
`

## 18. 异步进程与并发【后续设计】
`
正式链路拆为轻量Worker：
`
- Capture Worker：从MediaMTX拉流、解码、抽帧和维护环形缓冲。
- Inference Worker：集中加载YOLO，多源调度并更新Tracker。
- Event Producer：轨迹去重、候选触发、多帧选择并写Candidate Stream。
- VLM Consumer：限并发调用模型并输出分析结果。
- Saver：上传 MinIO、写 MySQL、发布告警事件。
- Manager：启动、心跳、优雅停止和崩溃拉起。

`
背压策略：队列超过阈值时降低采样率、丢弃旧的非关键帧、合并同 track 候选；关键告警不能无声丢弃。每条消息有幂等 ID、重试次数和过期时间。

## 21. Flask-Migrate 数据库迁移【已实现——阶段一】
`
### 21.1 为什么需要数据库迁移
`
在阶段一之前，数据库表是怎么创建的？
`python
# core/db.py（改造前）
def init_db(app):
    # ... 连接数据库 ...
    db.create_all()  # 应用启动时自动创建所有表
`
`
这段代码的意思是：每次 Flask 应用启动时，都会检查 models.py 里定义的所有模型，如果数据库里没有对应的表，就自动创建。
`
**原型阶段这样做没问题**，但一旦项目复杂起来，问题就来了：
`
| 问题 | 说明 |
|---|---|
| ❌ 无法追踪变更 | 谁在什么时候改了哪个字段，没有记录 |
| ❌ 无法回滚 | 改错了字段只能手动修复，没有"撤销"按钮 |
| ❌ 多环境不同步 | 开发、测试、生产环境的表结构可能不一致 |
| ❌ 无法增量更新 | 每次启动都重新创建所有表，做不到"只加一个字段" |
`
### 21.2 解决方案：Flask-Migrate + Alembic
`
Flask-Migrate 是 Flask 的数据库迁移插件，底层使用 Alembic。Alembic 是 SQLAlchemy 的迁移工具，它的工作方式是：
`
1. **对比差异**：把你当前的模型定义和数据库里的真实表结构对比
2. **生成迁移脚本**：自动生成 SQL 语句（CREATE TABLE、ALTER TABLE 等）
3. **版本管理**：每个迁移脚本都有一个版本号，可以前进（upgrade）也可以后退（downgrade）
`
### 21.3 改造后的代码
`
**core/db.py**：添加 Migrate 支持
`python
from flask_migrate import Migrate
`
db = SQLAlchemy()
migrate = Migrate()  # 全局的 migrate 对象
`
def init_db(app, create_tables: bool = False):
    \"\"\"初始化数据库连接。
    create_tables=False 是默认值，不再自动创建表。
    \"\"\"
    # ... 连接数据库配置 ...
    db.init_app(app)
    if create_tables:
        # 只有测试才用 create_all，生产环境用 flask db upgrade
        with app.app_context():
            db.create_all()
`
def init_migrate(app):
    \"\"\"注册 Flask-Migrate 到应用\"\"\"
    return Migrate(app, db)
`
`
**app.py**：在 create_app 中注册迁移
`python
from core.db import init_db, init_migrate
`
def create_app(register_metrics=True):
    app = Flask(__name__)
    init_db(app)       # 连接数据库，但不创建表
    init_migrate(app)  # 注册迁移命令
    # ...
`
`
### 21.4 迁移命令详解
`
`ash
# 1. 初始化迁移目录（只需要执行一次）
# 会在项目根目录创建 migrations/ 文件夹
flask db init
`
# 2. 生成迁移文件（每次改完模型后执行）
# alembic 会自动对比模型和数据库，生成迁移脚本
flask db migrate -m "描述本次变更"
`
# 3. 应用迁移（执行迁移脚本，修改数据库）
flask db upgrade
`
# 4. 回滚迁移（撤销上一次迁移）
flask db downgrade
`
# 5. 查看当前版本
flask db current
`
`
### 21.5 测试兼容
`
原有的测试代码使用 init_db(app, create_tables=True) 来保持向后兼容。这样测试不需要先跑迁移，速度更快。
`
### 21.6 面试话术
`
> 在项目初期，我使用 create_all() 自动建表。但考虑到后续会有多人协作和上线部署，我引入了 Flask-Migrate + Alembic 来做数据库版本管理。这样做的好处是：每个表结构变更都生成一个迁移脚本，纳入 Git 版本管理；上线时可以按版本回滚；开发、测试、生产环境的数据库结构通过迁移脚本保持一致。而且我改造的时候保证了旧测试代码不受影响，测试用例仍然可以用 create_tables=True 快速建表。
`

## 22. VideoSource 和 TaskRun 模型【已实现——阶段一】
`
### 22.1 为什么拆出 VideoSource
`
先看看改造前的 AnalysisTask 模型长什么样：
`python
class AnalysisTask(db.Model):
    __tablename__ = "analysis_tasks"
    
    id = Column(Integer, primary_key=True)
    name = Column(String(100), nullable=False)
    source_url = Column(String(500), nullable=False)  # 视频源地址直接写在这里
    source_type = Column(String(20))  # video/camera/stream
    # ... 其他字段
`
`
**这有什么问题？**
`
假设你要监控两个地方：东门和西门，每个门都要做"行人检测"和"车辆检测"两个任务。那你需要创建 4 个任务：
`
`
任务1: 东门行人检测, source_url="rtsp://admin:123456@192.168.1.1:554/stream1"
任务2: 东门车辆检测, source_url="rtsp://admin:123456@192.168.1.1:554/stream1"  ← 重复！
任务3: 西门行人检测, source_url="rtsp://admin:pass@192.168.1.2:554/stream1"
任务4: 西门车辆检测, source_url="rtsp://admin:pass@192.168.1.2:554/stream1"  ← 重复！
`
`
问题很明显：
- 同一个摄像头的 RTSP 地址重复写了多次
- 换了密码，要改 2 个任务而不是 1 个
- 凭据（密码）明文保存在 URL 里，API 返回时也会暴露密码

### 22.2 VideoSource 的设计
`
**核心思路**：把"摄像头是谁"和"分析什么"拆成两个独立实体。
`python
class VideoSource(db.Model):
    __tablename__ = "video_sources"
    
    id = Column(Integer, primary_key=True, autoincrement=True)
    name = Column(String(100), nullable=False, unique=True)  # 摄像头名称（唯一）
    source_type = Column(String(20), nullable=False)          # local_file/rtsp/rtmp/http
    url = Column(String(500), nullable=False)                 # 视频源地址
    media_mtx_path = Column(String(100), default="")          # MediaMTX 推流路径
    connection_status = Column(String(20), default="unknown") # unknown/checking/online/offline
    last_probe_at = Column(DateTime, nullable=True)           # 上次探测时间
    last_probe_ok = Column(Boolean, nullable=True)            # 上次探测是否成功
    width = Column(Integer, nullable=True)                    # 分辨率宽
    height = Column(Integer, nullable=True)                   # 分辨率高
    fps = Column(Float, nullable=True)                        # 帧率
    enabled = Column(Boolean, default=True)
    created_at = Column(DateTime, default=datetime.now)
    updated_at = Column(DateTime, default=datetime.now, onupdate=datetime.now)
    
    tasks = relationship("AnalysisTask", back_populates="video_source")
`
`
改造后的 AnalysisTask 不再直接存 URL，而是引用 VideoSource 的 ID：
`python
class AnalysisTask(db.Model):
    __tablename__ = "analysis_tasks"
    
    id = Column(Integer, primary_key=True)
    name = Column(String(100), nullable=False)
    source_url = Column(String(500), nullable=False)  # 兼容旧数据，保留
    source_type = Column(String(20), default="video")
    source_id = Column(Integer, ForeignKey("video_sources.id"), nullable=True)  # ← 新增
    # ...
    
    video_source = relationship("VideoSource", back_populates="tasks")
    runs = relationship("TaskRun", back_populates="task")
`

- 一个摄像头只创建一次 VideoSource，多个任务可以复用

## 23. URI 校验与凭据脱敏【已实现——阶段一】
`
### 23.1 为什么需要校验
`
用户输入的媒体源地址可能是这些东西：
`
`
# 合法地址
rtsp://admin:pass@192.168.1.1:554/stream1
`
# 路径遍历攻击（想读取系统文件）
../../../etc/passwd
..\\..\\..\\windows\\system32\\config
`
# 空字节注入（绕过安全检查）
test.mp4\\x00.exe
`
# 完全不合法
not-a-uri
`
`
如果不校验，攻击者可能：
- 读取服务器上的敏感文件（路径遍历）
- 让服务器访问内部网络（SSRF）
- 获取其他用户的凭据（凭据泄漏）

### 23.2 实现：media_source_validator.py
`
这个文件实现了三个核心功能：
`
**功能 1：URI 规范化**
`python
def normalize_uri(uri: str) -> dict:
    \"\"\"识别 URI 类型并返回标准格式\"\"\"
    if uri.startswith("rtsp://"):
        return {"normalized": uri, "source_type": "rtsp"}
    elif uri.startswith("rtmp://"):
        return {"normalized": uri, "source_type": "rtmp"}
    elif uri.startswith("http://") or uri.startswith("https://"):
        return {"normalized": uri, "source_type": "http"}
    elif "/" in uri or "." in uri:
        # 本地文件路径
        return {"normalized": str(Path(uri).resolve()), "source_type": "local_file"}
    else:
        return {"normalized": None, "source_type": None, "error": "无法识别的 URI 格式"}
`
`
**功能 2：路径安全检测**
`python
def is_path_safe(path: str) -> bool:
    \"\"\"检查文件路径是否安全\"\"\"
    # 1. 拒绝空字节
    if "\\x00" in path or "%00" in path:
        return False
    
    # 2. 拒绝路径遍历（../ 和 ..\\）
    normalized = path.replace("\\\\", "/")
    parts = normalized.split("/")
    if ".." in parts:
        return False
    
    # 3. 检查是否在允许的目录内
    try:
        p = Path(path).resolve()
        for allowed in allowed_dirs:
            p.relative_to(allowed)  # 如果不在 allowed 内会抛异常
            return True
        return False
    except (ValueError, RuntimeError):
        return False
`
`
**功能 3：凭据脱敏**
`python
def sanitize_credentials(uri: str) -> str:
    \"\"\"把密码替换为 ****\"\"\"
    parsed = urlparse(uri)
    if parsed.password:
        # 重构 URL，密码替换为 ****
        netloc = f"{parsed.username}:****@{parsed.hostname}"
        if parsed.port:
            netloc = f"{netloc}:{parsed.port}"
        return urlunparse((parsed.scheme, netloc, parsed.path, ...))
    return uri
`
`
**为什么要有两种脱敏函数？**
`
| 函数 | 用途 | 示例 |
|---|---|---|
| sanitize_credentials() | API 响应 | 
tsp://admin:****@host:554/stream |
| log_safe_url() | 日志输出 | 
tsp://****:****@host:554/stream |
`
API 响应中保留用户名方便识别，但日志中连用户名一起隐藏，防止日志泄露时被追踪到。
`
### 23.3 FFprobe 探测
`python
def probe_media(path: str) -> ProbeResult:
    \"\"\"用 FFprobe 探测媒体文件，获取分辨率、帧率等信息\"\"\"
    cmd = ["ffprobe", "-v", "quiet", "-print_format", "json", 
           "-show_format", "-show_streams", path]
    result = subprocess.run(cmd, capture_output=True, text=True, timeout=15)
    # 解析 JSON，提取视频流的宽、高、帧率
`
`
**为什么要用 subprocess.run 而不是 os.system？**
- subprocess.run 使用参数数组，不会把用户输入拼接到 shell 命令中
- 如果用户输入是 "; rm -rf /"，os.system 会执行这个命令，但 subprocess.run 只会把它当成 ffprobe 的一个参数

def start_task(task_id: int) -> TaskRun:
    \"\"\"启动任务。幂等：重复启动返回同一条记录\"\"\"
    task = get_task(task_id)
    if task is None:
        raise TaskServiceError(f"Task {task_id} not found")
    
    # 检查是否已经有一个 starting/running 的运行记录
    existing = TaskRun.query.filter(
        TaskRun.task_id == task_id,
        TaskRun.status.in_(["starting", "running"]),
    ).first()
    if existing:
        # 已经启动过了，返回现有的
        return existing
    
    # 创建新的运行记录
    snapshot = _build_config_snapshot(task)
    run = TaskRun(task_id=task_id, status="starting", config_snapshot=snapshot, ...)
    db.session.add(run)
    db.session.commit()
    return run
`

## 28. Capture Worker 与原始画面预览【已实现——阶段二切片 A】

### 28.1 这个模块解决什么问题

阶段一只解决了“任务是什么、视频源在哪里、如何启动和停止”这些控制面问题，还没有真正持续读取视频。Capture Worker 是 AI 数据链路的入口，负责把本地 MP4 或 RTSP 视频转换为统一内存帧，供后续 YOLO 消费。

```text
本地 MP4 / 摄像头 RTSP
        ↓
OpenCV VideoCapture 解封装、解码
        ↓
CaptureWorker 生成 FramePacket
        ↓
LatestFrameBuffer 有界缓冲与丢旧帧
        ├── MJPEG 调试预览
        └── 下一切片的 Inference Worker
```

Capture Worker 不加载 YOLO，也不调用 VLM。分离职责后，拉流故障、推理性能和业务规则可以独立测试，避免一个巨型循环中任何一步变慢都拖垮整条链路。

### 28.2 核心文件和职责

| 文件 | 职责 |
|---|---|
| `core/stream_client.py` | 封装 OpenCV `VideoCapture`，统一打开、读取、重启和释放 |
| `workers/contracts.py` | 定义跨模块传递的 `FramePacket` |
| `workers/frame_buffer.py` | 实现线程安全、有容量上限的最新帧缓冲 |
| `workers/capture_worker.py` | 后台拉流，处理 EOF、重连、节流和状态统计 |
| `core/runtime_manager.py` | 管理开发模式下每个任务的 Worker 和缓冲生命周期 |
| `web/routes/runtime.py` | 提供运行状态和 MJPEG 调试预览接口 |
| `web/templates/live_detection.html` | 展示原始画面、捕获、丢帧、重连和错误 |

核心 Worker 不导入 Flask，也不依赖 HTTP 请求，以后从 Web 进程拆为独立进程时不需要重写拉流逻辑。

### 28.3 `FramePacket` 为什么不能只传图片

除 NumPy BGR 图像外，`FramePacket` 还保存：

- `task_id`：属于哪个分析任务。
- `run_id`：属于哪次运行，防止任务重启前后的帧混合。
- `trace_id`：单帧链路追踪标识，可关联检测、跟踪和 VLM 日志。
- `frame_index`：源视频帧序号。
- `source_timestamp_ms`：帧在源视频时间轴的位置。
- `captured_at`：系统捕获时间，用于计算端到端延迟。
- `frame`：OpenCV 解码得到的 `HxWx3` BGR 图像。

构造时校验正数 ID、非空 `trace_id`、非负帧号和时间戳，以及图像必须是非空三通道 NumPy 数组。错误数据在入口就被拒绝，避免到 YOLO 阶段才发生难定位异常。

### 28.4 本地文件与 RTSP 的差异

| 场景 | 本地 MP4 | RTSP 实时流 |
|---|---|---|
| 是否有结尾 | 有 EOF | 理论上持续运行 |
| 读取速度 | 默认可能远快于真实 FPS | 通常受摄像头发送速度限制 |
| 失败处理 | 演示模式回到开头循环 | 断线后重新连接 |
| 时间戳 | 可读取文件时间轴 | 依赖流和 OpenCV 后端 |

本地视频按源 FPS 节流。例如 25 FPS 约每 40 ms 读取一帧，避免 45 秒视频几秒内读完，也让预览接近真实摄像头。RTSP 读帧失败则按上限重连，耗尽后进入 `failed` 并记录 `last_error`。

### 28.5 为什么缓冲满了丢最旧帧

实时分析追求“尽快知道现在发生了什么”，不是像离线转码一样保证每帧必处理。假设输入 25 FPS，而 CPU YOLO 只能处理 13 FPS：

```text
不丢帧：队列持续增长 → 页面看到几十秒前的画面
丢旧帧：跳过过期画面 → 保持较低实时延迟
```

`LatestFrameBuffer` 使用固定容量 `deque`。满时先删除最旧帧，再加入新帧并增加 `dropped_frames`。Inference Worker 后续还可用 `get_latest()` 取最新帧并清除中间积压。这就是背压：下游处理不过来时，系统主动限制内存并采用可接受降级。

丢帧数不能单独判断好坏，应与捕获 FPS、推理 FPS 和端到端 P95 一起看。“有限丢帧但延迟稳定”通常优于“不丢帧但延迟无限增长”。

### 28.6 Capture Worker 状态机与资源释放

```text
created → connecting → running → stopped
                  └────────────→ failed
```

- `created`：对象已创建，线程尚未连接。
- `connecting`：正在打开视频源。
- `running`：成功打开并持续读帧。
- `stopped`：正常 EOF 或外部停止。
- `failed`：源打不开、重连耗尽或发生异常。

`start()` 和 `stop()` 幂等，重复调用不会创建重复线程或报错。所有退出路径在 `finally` 中调用 `release()`，释放文件句柄、网络连接和解码资源。

停止后还要清空帧缓冲。1080p BGR 单帧约占 `1920 × 1080 × 3 ≈ 5.9 MiB`；如果只停线程，Python 仍持有多张大图像。为此新增了停止后 `buffer_size == 0` 的回归测试，并在停止、替换会话和 `stop_all()` 三条路径清理缓冲。

### 28.7 `RuntimeManager` 的作用和生产边界

当前为方便单笔记本联调，`RuntimeManager` 嵌入 Flask 进程：启动任务时创建缓冲和 Worker，用 `task_id` 注册会话，状态接口读取快照，预览接口读取最新帧，停止时停线程并清空缓冲。

这只是开发运行器。生产环境若启动多个 Web 实例，各进程内存互不共享，请求可能落到没有 Worker 的实例。阶段三会将 Capture/Inference 拆为独立 Worker，Web 通过 Redis 控制消息和心跳读取状态。

数据库 `TaskRun.status` 当前代表持久控制面状态，启动后保持 `starting`；Runtime API 返回当前进程内执行状态 `running`。不能在启动路由直接将数据库改成 `running`，否则 Worker 打不开视频时数据库会错误宣称运行成功。后续由 Worker 成功心跳推动持久状态转换。

### 28.8 MJPEG 为什么只用于调试

`GET /api/analysis-tasks/{id}/preview` 将最新 BGR 帧编码为 JPEG，以 `multipart/x-mixed-replace` 连续返回。浏览器 `<img>` 即可显示，很适合确认后端是否真的拿到 AI 将处理的帧。

但 MJPEG 每帧都是完整 JPEG，带宽高，没有成熟弱网自适应、音视频同步和播放控制；每个浏览器连接还会持续产生编码和 HTTP 输出开销。因此正式原视频预览仍使用 MediaMTX WebRTC/HLS，MJPEG 只是 AI 链路本地调试窗口。

### 28.9 接口、页面和增量展示策略

|---|---|---|---|
| `GET` | `/api/analysis-tasks/{id}/runtime` | 查询 Capture 状态和计数 | 不存在 `404`；未启动 `409` |
| `GET` | `/api/analysis-tasks/{id}/preview` | 返回 MJPEG 原始帧 | 未运行或无帧时返回明确错误 |

页面展示状态、捕获帧数、背压丢帧、重连次数、缓冲帧数、最近帧时间和错误。下一切片会在同一页面增加 YOLO 检测框、人数、推理 FPS 和延迟。这样每完成一个核心模块就同时完成接口和可视化，尽早发现接口契约与展示问题。

## 29. 集中式 Inference Worker 与 YOLO 检测画面【已实现——阶段二切片 B】

### 29.1 这个模块解决什么问题

切片 A 已能持续产出帧，但还没有消费者。切片 B 把 YOLO 接到实时链路中，并把检测结果、带框画面和工程指标统一交给 Runtime API：

```text
多个 Capture Worker
      ↓ 每路一个 LatestFrameBuffer
集中式 Inference Worker（共享一个 YOLO）
      ↓
FrameDetections + InferenceResult + 指标快照
      ├── detection-preview 带框 MJPEG
      └── live 页面人数、FPS、耗时、P95
```

本切片只做目标检测，不做轨迹关联、行为理解和最终告警。下一切片 Tracker 会消费这里的检测框；后续 VLM 只接收筛选后的候选片段，而不是接收每一帧。

### 29.2 为什么一个模型服务多路视频

每路视频各加载一个 YOLO 最简单，但权重、计算图和中间张量会重复占用内存或显存。单机 RTX 4050 显存有限，多实例还会争抢 GPU，导致上下文切换、显存不足和吞吐抖动。

当前 `InferenceWorker` 延迟加载一个检测器，再轮询所有任务缓冲。这样做有三个收益：

1. 权重只加载一次，降低内存和显存占用。
2. 模型生命周期集中管理，便于后续批处理、ONNX/TensorRT 和热更新。
3. 单任务坏帧只计入该任务失败，不会停止其他任务。

代价是所有任务共享同一个推理线程。某一路超大分辨率或模型调用卡住时会影响其他路，因此必须有公平轮询、输入尺寸约束、超时与指标。当前先服务单机演示，生产扩容可按 GPU 或任务组启动多个集中式 Worker，而不是退回“每路一个模型”。

### 29.3 公平轮询怎样工作

Worker 用 `deque` 保存任务顺序。每次 `process_next()` 把队首任务移到队尾，并寻找第一个有帧的缓冲：

```text
[任务1, 任务2, 任务3]
处理任务1后 → [任务2, 任务3, 任务1]
处理任务2后 → [任务3, 任务1, 任务2]
```

空缓冲会被跳过，但仍保留在轮询队列中。这样持续有帧的任务不能永久霸占模型。当前是基础 Round Robin，不根据分辨率、优先级或 SLA 加权；多租户生产场景可扩展为加权轮询或令牌桶。

### 29.4 为什么每次只取最新帧

`LatestFrameBuffer.get_latest()` 返回最新帧，并删除更旧的积压帧。假设 Capture 已写入帧 101、102、103，而 YOLO 此时才有空：系统直接处理 103，并把 101、102 计为 `stale_frames_discarded=2`。

这里有两种不同丢帧：

- `Capture dropped_frames`：生产者写入时缓冲已满，最旧帧被容量策略淘汰。
- `Inference stale_frames_discarded`：消费者开始处理时主动跳到最新帧，清理尚未处理的旧帧。

两者都服务于实时性，但发生位置不同，必须分开统计。否则只能看到总丢帧，无法判断是缓冲容量太小，还是模型处理速度跟不上输入。

### 29.5 数据如何从帧变成检测结果

```text
FramePacket
  frame + task_id/run_id/trace_id/时间戳
        ↓ detector.detect()
FrameDetections
  检测框 + 类别 + 置信度 + 模型分阶段耗时
        ↓ 绘框并绑定原始包
InferenceResult
  packet + detections + annotated_frame
```

复用 `ai/yolo_detector.py` 的 `FrameDetections`，没有再创建重复检测 DTO。`InferenceResult` 保存原始 `FramePacket`，因此后续 Tracker 和日志仍可沿用 `task_id`、`run_id`、`trace_id` 与源时间戳。

OpenCV 图像是 BGR 排列。绘框在副本上进行，绿色框颜色为 `(0, 255, 0)`，不会修改 Capture 缓冲中的原图。坐标在绘制前限制到图像边界，避免模型浮点框越界导致异常。

### 29.6 指标的准确含义

| 指标 | 定义 | 用途 |
|---|---|---|
| `preprocess_ms` | 缩放、归一化和张量准备耗时 | 判断输入处理瓶颈 |
| `inference_ms` | 模型前向计算耗时 | 比较模型、设备和精度模式 |
| `postprocess_ms` | NMS、类别过滤和结果转换耗时 | 判断框数量是否拖慢后处理 |
| `end_to_end_ms` | `captured_at` 到检测完成的墙钟时间 | 衡量用户看到结果有多旧 |
| `end_to_end_p95_ms` | 最近窗口中 95% 帧不超过的端到端延迟 | 观察尾延迟与抖动 |
| `inference_fps` | 已处理帧数 ÷ 累计推理忙碌秒数 | 衡量 Worker 真正工作时的吞吐 |

`inference_fps` 不能用“注册任务到现在的总时间”计算，因为没有视频帧时 Worker 在等待，把空闲时间算进去会错误降低模型吞吐。每帧忙碌时间取“真实墙钟检测时间”和检测器报告 `total_ms` 的较大值，兼容真实模型和测试替身。

端到端 P95 包含排队和冷启动。真实冒烟中首轮加载模型使 P95 约为 4.8 秒，而稳定帧端到端约几十毫秒；这不是矛盾。生产压测应先记录冷启动指标，再预热模型并单独报告稳态 P50/P95/P99。

### 29.7 延迟加载与两把锁

应用启动时不立即加载 YOLO。只有第一帧需要推理时，`detector_factory` 才创建后端和模型，优点是 Web/API、迁移和不涉及 AI 的测试不会付出模型启动成本。

初版排障发现，如果在 Worker 状态锁中加载模型，模型下载或初始化可能持续几十秒，此时 `task_snapshot()` 也拿不到同一把锁，页面看起来像整个系统卡死。修复后：

- `_lock` 只保护任务字典、指标、结果和轮询队列。
- `_detector_lock` 只保护检测器单例创建。

耗时模型加载不能长期持有状态锁。新增慢工厂并发测试证明：一个线程正在加载模型时，另一个线程仍能快速读取任务快照。

### 29.8 Runtime、接口与页面怎样接起来

`RuntimeManager` 只持有一个共享 `InferenceWorker`。启动任务时先确保推理线程运行，再注册该任务的帧缓冲；同一任务换新 `run_id` 时，先停止旧 Capture、注销旧推理状态、清空旧缓冲，再注册新会话；停止任务时同样注销并释放。

| 方法 | 路径 | 作用 | 主要异常 |
|---|---|---|---|
| `GET` | `/api/analysis-tasks/{id}/runtime` | 返回 Capture 与 Inference 嵌套指标 | 任务不存在 `404`；未启动 `409` |
| `GET` | `/api/analysis-tasks/{id}/detection-preview` | 连续返回最新带框 JPEG | 任务不存在 `404`；未启动 `409` |
| `GET` | `/live/{task_id}` | 展示检测画面和两类 Worker 指标 | 接口错误时展示状态，不伪造数据 |

页面显示检测人数、已处理帧、推理 FPS、三阶段耗时、端到端延迟、P95 和推理丢旧帧。原始 `/preview` 仍保留，便于区分“拉流就失败”还是“YOLO 没有结果”。

### 29.9 `YOLO_HALF=false` 缺陷怎样发现和修复

真实冒烟输出 `half=True`，但 `.env` 明确写了 `YOLO_HALF=false`。排查发现配置层只覆盖了 `YOLO_DEVICE` 和 `YOLO_MODEL`，完全没有读取 `YOLO_HALF`；代码默认值还残留为 `True`。

修复采用 TDD：先设置环境变量并断言结果应为 `False`，确认测试失败；再新增严格 `_env_bool()`，支持常见真假写法，非法值直接抛出 `ValueError`；最后把 `YoloConfig.half` 默认值改为 `False`。不能写 `bool(os.getenv("YOLO_HALF"))`，因为 Python 中任何非空字符串都为真，包括 `"false"`。

CPU 不应开启 FP16。半精度主要用于支持 FP16 的 GPU 加速；当前显卡异常时固定 `device=cpu, half=False`，避免自动探测导致不同机器行为不一致。

### 30.6 HLS 就绪轮询（替换 `time.sleep(2)`）

**根因**：FFmpeg 从 `Popen` 到真正把 RTSP 推起来、MediaMTX 再转成 HLS playlist 可写，不是固定耗时。2 秒有时够有时不够，Runtime 一去拉 HLS 就 404，运行状态直接翻车。

**新实现**（`web/routes/monitor.py`）：

```python
def _wait_hls_ready(url, timeout, interval, ffmpeg_proc=None) -> bool:
    deadline = time.monotonic() + timeout
    while time.monotonic() < deadline:
        if ffmpeg_proc is not None and ffmpeg_proc.poll() is not None:
            return False  # 推流进程已退出，没必要再等
        try:
            with urllib.request.urlopen(url, timeout=1.0) as resp:
                if 200 <= resp.status < 300:
                    if b"#EXTM3U" in resp.read(64):
                        return True
        except (URLError, HTTPError, TimeoutError, OSError):
            pass
        time.sleep(interval)
    return False
```

要点：

- 用 `time.monotonic()` 算 deadline，避免系统时间调整时误判；
- 校验的是 HLS playlist 首字节 `#EXTM3U`，比只看 200 OK 更严格；
- 探测过程中若 FFmpeg 已 `poll() != None`，立即失败，不再消耗剩余超时；
- 超时或失败会 kill FFmpeg、`_ffmpeg_procs.pop`、`task.status = "failed"`、`run.status = "failed"`，并返回 504 `HLS_NOT_READY`，前端能拿到明确 code。

### 30.7 MJPEG 预览三次重试

## 31. 任务持久化与前端状态恢复【已实现——本轮】

### 31.1 解决的问题

用户反馈："点击实时监测选项卡后页面刷新，之前分析的视频、日志、任务信息全部丢失。"

排查后发现这不是数据丢失，而是**两层缺口叠加**：

1. **前端瞬态状态未持久化**：`currentTaskId`、上传进度、检测预览等全是 JS 内存变量，页面一刷新就清零。
2. **缺少历史入口**：虽然 MySQL 里任务记录都在，但前端没有"历史记录"页面可以查看和恢复。
3. **视频文件只存本地磁盘**：`data/videos/uploads/` 目录里的文件一旦被清理，任务记录就成了空壳。

### 31.2 三层修复架构

```
┌─────────────────────────────────────────────────┐
│  Layer 1: localStorage (前端瞬态恢复)            │
│  - currentTaskId 存入 localStorage              │
│  - URL ?task_id=xxx 支持直接链接恢复            │
│  - 页面加载时 rehydrateFromTask() 拉后端状态    │
├─────────────────────────────────────────────────┤
│  Layer 2: MySQL (任务元数据持久化)              │
│  - VideoSource / AnalysisTask / TaskRun        │
│  - /history 页面列出所有历史任务               │
│  - 顶栏"最近任务"下拉快速切换                   │
├─────────────────────────────────────────────────┤
│  Layer 3: MinIO (视频文件持久化)               │
│  - 上传时自动 put_object 到 videos bucket     │
│  - VideoSource.storage_uri 记录对象路径        │
│  - start-pipeline 时本地文件丢失则从 MinIO 恢复 │
└─────────────────────────────────────────────────┘
```

### 31.3 Layer 1: 前端 rehydrate

**核心逻辑**（`web/templates/monitor/index.html`）：

```js
(function tryRehydrate() {
    // 优先级：URL query > localStorage > 空白
    const params = new URLSearchParams(window.location.search);
    let taskId = params.get("task_id") ? parseInt(params.get("task_id")) : null;
    if (!taskId) {
        const stored = localStorage.getItem("currentTaskId");
        if (stored) taskId = parseInt(stored);
    }
    if (taskId && !isNaN(taskId)) rehydrateFromTask(taskId);
})();
```

`rehydrateFromTask(taskId)` 做了三件事：
1. `GET /api/analysis-tasks/{id}` 拉任务元数据，填充任务信息面板；
2. `GET /api/analysis-tasks/{id}/runtime` 检查是否正在运行；
3. 如果运行中则自动打开 MJPEG 预览 + 恢复指标轮询；如果未运行则启用"开始分析"按钮。

**关键点**：上传成功后 `localStorage.setItem("currentTaskId", taskId)`，这样即使用户切到其他 Tab 再回来，也能自动恢复。

### 31.4 Layer 2: 历史记录页

**路由**：
- `GET /history` → `web/templates/monitor/history.html`

**历史页功能**：

### 31.7 修复的 Bug

1. **`extra_js` 块位置错误**：`base.html` 的 `{% block extra_js %}` 原本在内联 `<script>` 标签内部，Jinja2 渲染后子页面的 JS 代码被嵌套在父页面的脚本里，导致语法错误。修复：将 `{% block extra_js %}` 移到 `</script>` 之后。

4. **`TaskRun.config_snapshot` NOT NULL**：手动创建 TaskRun 时缺少必填字段。修复：调用 `_build_config_snapshot(task)`。
5. **同名文件二次上传违反 UNIQUE 约束**：`VideoSource.name` 加了 6 位 hex 后缀。
6. **全局 JSON 错误处理器**：`/api/*` 下未捕获异常不再返回 HTML，前端能显示准确错误码。
